# Учёт гаражного кооператива

Flask + SQLAlchemy + SQLite. Роли доступа (по возрастанию прав): `member`
(рядовой член) → `board` / `accountant` (правление и бухгалтер — одинаковый
уровень прав) → `chairman` (председатель — самая широкая, включая учётные
записи и правку чужих ошибок).

## Установка и запуск

```bash
python -m venv venv
source venv/bin/activate        # Windows: venv\Scripts\activate
pip install -r requirements.txt

python seed.py                  # создаст БД (instance/coop.db), пользователя chairman и базовые виды взносов
python run.py                   # http://127.0.0.1:5000
```

Логин по умолчанию: `chairman` / `change-me-please` — смените пароль сразу
после первого входа в «Мой профиль» → «Изменить пароль» (доступно любому
пользователю для своей же учётной записи; для сброса пароля кому-то
другому — председатель, через «Учётные записи» → «Сбросить пароль», но
только если тот пользователь уже привязан к карточке человека `Person`).

`weasyprint` в `requirements.txt` нужен только для кнопки «Скачать PDF» на
странице печати ПД-4 (`/pd4/print/pdf`) — без него всё остальное, включая
печать через браузер (`Ctrl+P`), работает как обычно; если библиотека не
поставится (нужны системные зависимости Pango/Cairo), просто пропустите её.

### Автоматизация (cron)

Ключевая ставка ЦБ РФ (нужна для расчёта пени) и так пересчитывается «на
лету» при каждом открытии дашборда/страницы «Пеня» (см. ниже), но чтобы
она была свежей ещё до того, как кто-то из правления зайдёт в приложение
(например, в выходные), можно поставить в cron ежедневное обновление:

```bash
# crontab -e
0 6 * * * /путь/к/проекту/scripts/update_key_rate.sh
```

Скрипт сам подхватывает venv проекта (если есть `.venv/` или `venv/`),
пишет лог в `instance/logs/update_key_rate.log` и не даёт двум запускам
пересечься (`flock`). Запустить вручную для проверки:
`python3 scripts/update_key_rate.py`.

## Схема БД, индексы и внешние ключи

Во всех таблицах на внешние ключи и часто фильтруемые/сортируемые поля
(даты, `full_name`, `year` и т.д.) добавлены индексы (`index=True`), а для
внешних ключей — явные политики `ON DELETE`:
- `CASCADE` — там, где дочерняя запись бессмысленна без родителя (телефоны
  человека, фото/собственники/пломбы гаража, показания счётчика, разнесение
  платежа по начислению)
- `SET NULL` — для необязательных ссылок (секретарь/председатель собрания,
  прикреплённый документ, плательщик, начисление ↔ показание счётчика)
- без явной политики (по умолчанию — запрет) — там, где удаление должно быть
  осознанным действием, а не побочным эффектом (нельзя удалить контрагента,
  человека или вид взноса, если на них ссылаются другие записи)

Проверка внешних ключей включена на уровне SQLite (`PRAGMA foreign_keys=ON`
при каждом подключении, `app/database.py`) — по умолчанию SQLite её не
делает, и без этого все `ondelete`/ограничения целостности просто
игнорировались бы.

**Миграции.** Проект использует Alembic (`alembic.ini`, `migrations/`).
При каждом старте `create_app()` (в т.ч. из `seed.py` и `run.py`) сам
вызывает `alembic upgrade head` (см. `app/database.py: run_migrations`) —
руками запускать ничего не нужно, схема БД подтягивается автоматически,
существующие данные не трогаются. История миграций сведена к одной
baseline-ревизии (`baseline current db schema`) — она описывает текущую
схему `app/models.py` целиком, старые пошаговые миграции удалены как
исторический артефакт разработки, а не часть боевого состояния (проект ещё
не разворачивался на реальных данных кооператива — сбрасывать историю
после уже накопленных боевых данных было бы неправильно, тут это делалось
осознанно и только по этой причине). Для уже существующей БД, заведённой
ещё до перехода на Alembic (нет таблицы `alembic_version`, но есть таблица
`user` — то есть боевые данные кооператива), при первом запуске
происходит не накат таблиц заново (упало бы на «уже существует»), а
`alembic stamp head`: её схема на момент перехода совпадает с
baseline-миграцией, поэтому просто помечается текущей.

Если вы поменяли что-то в `app/models.py`, порядок такой:
```bash
alembic revision --autogenerate -m "короткое описание изменения"
```
- Откройте свежий файл в `migrations/versions/` и **проверьте, что Alembic
  правильно понял изменение** (особенно при переименовании колонки —
  autogenerate увидит это как `drop` + `add` и молча потеряет данные в
  колонке; в таком случае руками замените на `op.alter_column(...,
  new_column_name=...)` или `batch_op.alter_column(...)`).
- Примените: `alembic upgrade head` (или просто перезапустите приложение —
  оно сделает это само).
- Откат при необходимости: `alembic downgrade -1`.

SQLite почти не умеет `ALTER TABLE` (нельзя удалить колонку, изменить тип,
добавить constraint) — поэтому `migrations/env.py` включает
`render_as_batch=True`: Alembic пересоздаёт таблицу во временную копию,
переносит все строки и переименовывает её обратно, вместо прямого `ALTER`.
Это и есть механизм, благодаря которому обновления схемы не стирают данные
кооператива — раньше (см. `context.md`, там это описано как повторяющийся
«нюанс» почти в каждой сессии) единственным способом было `rm
instance/coop.db && python seed.py`, что боевые данные бы уничтожило.

## Что уже реализовано

### Гараж — карточка и электричество
- Номер, площадь, приватизация земли, комментарий (правит только правление);
  собственники с долями владения (начисления по видам взносов автоматически
  распределяются пропорционально доле; если сумма долей ≠ 1 — жёлтый бейдж
  на карточке, но начисление всё равно проходит); контактные лица; фото с
  галереей-лайтбоксом (загружает и правит только правление)
- **Счётчик электричества** — история замен (номер, дата установки, дата
  опломбировки, показания при установке, номер пломбы на счётчике и на
  вводном автомате); актуальным считается последний по дате установки;
  кнопка «Добавить прибор учёта» / «Заменить прибор учёта» (текст зависит от
  того, стоит ли уже счётчик) открывает модальное окно
- **Ввод показаний** — доступен собственнику гаража и правлению; новое
  показание не может быть меньше предыдущего *этого конкретного счётчика*
  (если счётчик заменили — точка отсчёта заново от его показаний при
  установке, старая история не мешает); председатель дополнительно может
  исправить именно последнее внесённое показание через отдельную модалку
  (если его ошибочно ввёл рядовой член) — сумма начисления по нему
  пересчитывается автоматически
- **Начисление за электричество** считается автоматически: (новое показание
  − предыдущее) × тариф, действующий на дату снятия показаний; создаётся
  сразу с привязкой к конкретному показанию (`Charge.reading_id`)
- **Ручное начисление отдельного вида взноса на выбранное подмножество
  гаражей** — теперь часть страницы «Массовое начисление» (см. раздел
  «Финансы и справочники» ниже): выбор гаражей чекбоксами необязателен —
  если ничего не отмечено, начисление, как и раньше, идёт на все гаражи.
  Отдельная страница «Начисления на гаражи» (`/garages/charges/add`)
  удалена — она дублировала «Массовое начисление», только без стратегий
  расчёта (по коэффициенту / по площади / земельный налог) и без выбора
  подмножества гаражей; обе возможности объединены в одном месте
- **Объединённый «Журнал показаний и начисления»** на одну таблицу: дата,
  показания, тариф, сумма начисления (с бейджем «оплачено» / «частично: N ₽»
  / «не оплачено»), и тут же — кто/когда/сколько заплатил именно по этому
  начислению. Разнесение платежей по начислениям — по-настоящему в БД
  (`ChargeAllocation`), не текстовым сопоставлением: `FIFO` в обе стороны —
  старые начисления закрываются старыми платежами; пересчитывается заново
  при каждом новом начислении или платеже на гараж. Переплата/аванс, для
  которых пока нет открытого долга, — отдельной строкой с пометкой «аванс»
- **Регистрация платежа** — доступна только председателю и бухгалтеру (не
  рядовому члену и не обычному правлению); по умолчанию подставляются:
  сегодняшняя дата, плательщик — тот из собственников гаража, кто платил
  последним (список отсортирован по дате последнего платежа, новые сверху),
  сумма — текущая задолженность по счёту

### Кабинет члена кооператива (`/cabinet`)
- «Мой профиль» — правка своих контактов (телефоны, email, telegram,
  адреса, комментарий); ФИО/паспорт/членство — только просмотр. Изменения
  уходят на модерацию правлению как заявка (`PersonDataRevision`) —
  применяются в карточку только после одобрения
- «Мой гараж» — для каждого своего гаража: строка «Электроэнергия» (номер
  счёта, баланс) первой, затем счета по видам взносов (членские, налоги и
  т.д.); у каждой строки с задолженностью — кнопка 💳 «Оплатить», ведущая на
  готовую квитанцию ПД-4 именно по этому счёту

### Печать ПД-4 (`/pd4`)
- Квитанция по стандарту ГОСТ Р 56042-2014 с QR-кодом (генерируется через
  `segno`, PNG прямо в `<img>`, без JS-библиотек)
- **Права разделены по видам платёжек, не по ролям целиком**: правление
  видит список всех счетов с задолженностью и печатает выборочно по
  нескольким людям сразу (`/pd4/`) — но **только взносы/налоги/пеню**,
  доступа к электричеству через этот административный путь нет вообще,
  даже если явно указать гараж. Рядовой член печатает **любые** свои
  платёжки — и взносы, и электричество — по всем гаражам, которыми
  владеет полностью или частично; для member-счетов и для электросчёта
  гаража используется общий шаблон и общий механизм сборки (слипы обоих
  видов можно смешивать в одном списке — они дают одинаковый интерфейс
  шаблону), в «ФИО плательщика» электросчёта подставляются все текущие
  собственники через запятую. Электричество выставляется на гараж целиком
  (общий счётчик) — частичный собственник видит и может оплатить весь
  остаток долга гаража, не только свою долю пропорционально; взносы,
  наоборот, изначально разные лицевые счета на разных совладельцев
- Кнопка «Назад к выбору» на печатной странице — только у правления (это
  они выбирают печать по нескольким людям через `/pd4/`); у рядового
  члена не показывается ни для одного вида платёжки
- Каждая сформированная квитанция сохраняется в истории (`PD4Document`, с
  привязкой либо к member-счёту, либо к электросчёту гаража — ровно один из
  двух, проверяется constraint'ом в БД)
- «Скачать PDF» — опционально, требует `weasyprint`; работает для обоих
  видов платёжек и для смешанных наборов; печать через браузер работает
  всегда, независимо от наличия `weasyprint`

### Финансы и справочники
- **Лицевые счета членов** (`/finance`) — заводятся по видам взносов
  (справочник настраиваемый, есть признак «пеня»); начисления/платежи,
  ручной ввод номера счёта или автоформат по настраиваемому шаблону
- **Массовое начисление** (только председатель) — по коэффициенту гаража,
  пропорционально площади от общей суммы, либо автоматический расчёт
  земельного налога по кадастровой стоимости; можно ограничить выбором
  подмножества гаражей чекбоксами (с поиском по номеру/собственнику,
  кнопками «Выбрать все» / «Снять все») — если ничего не отмечено,
  начисление, как и раньше, идёт на все гаражи сразу. Раньше выбор
  подмножества жил отдельной страницей «Начисления на гаражи»
  (`/garages/charges/add`, доступной всему правлению, без стратегий
  расчёта) — она дублировала эту страницу и была удалена, обе возможности
  объединены здесь (правило доступа осталось таким, как было у «Массового
  начисления», — только председатель, а не всё правление)
- **Электроэнергия** (`/power`, правление) — история тарифов; поставщик
  выбирается из общего справочника контрагентов (не отдельная форма —
  реквизиты и вся история расчётов с ним смотрятся на его карточке в
  разделе «Контрагенты», сюда выведен только сам выбор и текущий баланс
  расчётов с ним со ссылкой на полную историю)
- **Показания общего (вводного) счётчика** — по месяцам, с защитой от
  повторного ввода за один и тот же месяц; при сохранении автоматически
  создаётся расход перед выбранным поставщиком (`Expense`, сумма = (новое
  показание − предыдущее) × тариф, действующий на дату); в форме можно сразу
  же отметить его оплаченным, выбрав расчётный счёт списания — тогда сумма
  сразу спишется с фактического баланса счёта (см. ниже) и создастся платёж
  контрагенту. Можно удалить только самое последнее показание (иначе
  исказились бы уже сохранённые суммы последующих записей) и только если по
  нему ещё нет оплаты. Отдельная более ранняя реализация «Общий счётчик»
  (`/electricity/master`) дублировала эту функциональность и была удалена
- **Контрагенты** (`/counterparties`, правление) — карточка (ИНН/КПП,
  категория, контакты, необязательный начальный баланс на дату, если
  расчёты с контрагентом велись ещё до учёта в системе) и полноценный учёт
  расчётов, зеркальный уже существующему учёту по лицевым счетам членов, но
  в обратную сторону (кооператив — плательщик, не получатель):
  - **Расходы** (`Expense`) — начисленный долг кооператива перед
    контрагентом, с прикреплённым подтверждающим документом (счёт/акт);
    заводятся вручную с карточки контрагента (для любых расходов — снег,
    видеонаблюдение, электрика и т.п.) либо автоматически при внесении
    показаний общего счётчика (см. выше, для поставщика электричества)
  - **Платежи** (`CounterpartyPayment`) — фактическая оплата, с привязкой к
    расчётному счёту списания (баланс счёта сразу уменьшается) и отдельным
    платёжным документом (платёжка/квитанция); разносятся по расходам
    по `FIFO` через реальные записи в БД (`ExpenseAllocation`, зеркало
    `ChargeAllocation`) — у каждого расхода виден статус «оплачено» /
    «частично: N ₽» / «не оплачено»
  - **Правка последнего платежа** — если ошиблись в сумме/дате при вводе;
    доступна только для самого последнего (по дате) платежа контрагенту, и
    только пока он не сторнирован — старые платежи задним числом не
    правятся, для них есть сторно (см. ниже)
  - **Сторно** — отменяющая проводка для платежа, который реально ушёл в
    банк (с ошибкой в реквизитах/организации), а потом вернулся — банком
    или самим контрагентом. Исходный платёж не трогается и остаётся в
    истории как есть, рядом создаётся запись с отрицательной суммой:
    компенсирует его эффект на баланс расчётов и возвращает сумму обратно
    на счёт списания. В отличие от правки — доступна для любого платежа
    (не только последнего), один платёж можно сторнировать только один раз
  - **Акты сверки** — период, наш расчётный баланс на дату и баланс по
    данным контрагента (если расходятся — виден бейдж «расхождение»),
    прикреплённый скан подписанного акта; на суммы расходов/платежей не
    влияют, чисто информационная запись
- **Автоматическое начисление пени** (`/finance/penalty`) — по
  просроченным взносам/налогам членов кооператива (только они — не
  электричество). Срок оплаты — единая по уставу дата в году
  (день/месяц в реквизитах кооператива, «Реквизиты» → «Пеня»). Формула:
  сумма непогашенного остатка конкретного начисления × ключевая ставка
  ЦБ РФ, действующая на день, × 1/300 (первые 30 дней просрочки) или
  1/150 (с 31-го дня), просуммированная по дням просрочки — считается
  точно, по датам реальных частичных платежей, а не по балансу счёта в
  целом. Ключевая ставка ЦБ РФ хранится в отдельной таблице (история по
  датам действия) — подгружается с официального SOAP-сервиса cbr.ru
  (правление) или вносится вручную, если сайт недоступен. Начисляет
  правление сама пеню как отдельные `Charge` на счёт-«близнец» (тот же
  механизм, что уже был у видов взносов с признаком «пеня» — если для
  вида взноса такого счёта нет, начисление по нему пропускается со
  списком «пропущено» в результате, без падения). Расчёт идемпотентен:
  повторный запуск на ту же дату не задваивает начисления, на более
  позднюю — досчитывает только новые дни; запускает расчёт (создаёт
  начисления) только председатель, загрузка/ввод ставки ЦБ — любой член
  правления

### Люди и учётные записи
- **Люди** (`/persons`) — ФИО, телефоны, адреса регистрации/проживания,
  email, telegram, паспортные данные РФ, даты вступления/выхода из членов
  кооператива, комментарий, флаги роли (правление/председатель/бухгалтер).
  Список видит только правление; карточку конкретного человека — правление
  (любую) или сам человек (только свою — по привязке учётной записи к
  `Person`); панель «Доступ в систему» на этой странице расположена справа
  от таблицы личных данных, видна только правлению. Флаги роли теперь
  только отображаются (бейджи «Председатель»/«Бухгалтер»/«Член правления»),
  править их напрямую на карточке человека больше нельзя — старые чекбоксы
  убраны, единственный способ менять состав правления теперь — страница
  «Правление» (см. ниже), с обязательной привязкой к протоколу собрания
- **Правление** (`/governance`) — созывы правления и составы ревизионной
  комиссии, каждый обязательно привязан к протоколу общего собрания
  (`GeneralMeeting`). Просмотр — любому залогиненному; создание созыва/
  комиссии и правка состава — только председателю. Новый созыв/состав
  автоматически закрывает предыдущий (проставляет ему дату окончания);
  добавление/удаление людей в состав само по себе не меняет прав входа в
  систему — это делает отдельная явная кнопка «Применить состав к правам
  доступа» на странице созыва (пересчитывает флаги `is_board_member` /
  `is_chairman` у всех людей по списку состава и синхронизирует роль
  привязанной учётной записи). Кнопка отделена от самого редактирования
  списка намеренно: если бы состав применялся к правам сразу при каждом
  добавлении строки, председатель, ещё не успевший внести самого себя в
  новый созыв, рисковал бы на полпути потерять доступ к этой же странице.
  Каждый член созыва явно отмечен либо «председатель», либо «член
  правления» (плюс необязательное текстовое поле для доп. роли — секретарь,
  казначей и т.п.). Ревизионная комиссия — только запись состава и
  председателя комиссии, на права входа не влияет (компетенция другая); при
  добавлении в комиссию действующего члена правления — мягкое
  предупреждение (устав обычно требует независимости комиссии от
  правления), без жёсткой блокировки
- **Бухгалтер** — назначается председателем отдельно от созывов правления
  (не выборная общим собранием должность, поэтому без протокола и без
  привязки к составу): на той же странице «Правление» — блок «Бухгалтер» с
  «Назначить»/«Снять», доступный любому человеку из справочника, не
  обязательно члену правления (может быть на аутсорсе — для входа в
  систему достаточно завести учётную запись через «Учётные записи»).
  Применение состава созыва к правам доступа назначение бухгалтера не
  трогает — это независимые механизмы
- **Учётные записи** (только председатель) — создание, сброс пароля другому
  пользователю, смена логина, включение/отключение, привязка/отвязка к
  карточке человека
- **Смена собственного пароля** — доступна любому залогиненному пользователю
  из «Мой профиль» (проверка текущего пароля, минимум 4 символа)
- Заявки на изменение собственных данных из личного кабинета — отдельный
  список, одобрение/отклонение с применением изменений в карточку

### Документы, собрания, реквизиты
- **Документы** — устав/приказы/акты/письма/протоколы, с загрузкой файла
- **Общие собрания** — дата, повестка, секретарь, председательствующий,
  протокол (загрузка файла прямо из модалки создания); служат основанием
  для созывов правления и составов ревизионной комиссии (см. выше)
- **Реквизиты кооператива** — ИНН/КПП/ОГРН, площади (кооператива, под
  гаражами, общего пользования); краткое название используется в шапке
  вместо статичного «ГСК»; несколько расчётных счетов (в одном или разных
  банках), с пометкой основного — именно он берётся для ПД-4; у каждого
  расчётного счёта отдельно — фактический баланс (вносится вручную, банк
  напрямую не подключён) с датой сверки. Поле «Баланс» самого кооператива
  (в отличие от баланса каждого расчётного счёта) — не хранится в БД,
  считается на лету как `accounting.cooperative_balance()` — сумма по всем
  расчётным счетам (сколько реально денег у кооператива), не путать с
  `receivables_balance()` (сколько члены должны/переплатили — отдельная
  метрика, нигде в UI сейчас не выведена). Расчётные
  счета целиком, а также поля «Баланс» и «Комментарий» в реквизитах —
  видны только правлению (`is_board()`), остальные реквизиты — всем
- **Электронное голосование** (`/voting`) — очно-заочное или заочное,
  альтернатива очному собранию, когда не удаётся очно собрать всех
  собственников. Председатель создаёт голосование (черновик), формирует
  повестку из одного или нескольких вопросов (у каждого — свой
  настраиваемый порог принятия, напр. 0.5 для простого большинства или
  0.6667 для квалифицированного), затем явно открывает приём бюллетеней
  на заданный период. Голосуют владельцы гаражей — вес голоса человека
  равна сумме его долей владения по всем его гаражам, так что «1 гараж —
  1 голос», а при нескольких собственниках гаража их голос делится ровно
  по долям, без специального кода под этот случай. Переголосование, пока
  приём открыт, разрешено — учитывается последняя подача. Кворум — жёсткое
  правило: голосование правомочно, только если приняло участие строго
  больше 50% от общего числа голосов кооператива; порог принятия по
  каждому вопросу считается от общего числа голосов кооператива (не от
  числа проголосовавших) — вопрос не считается принятым без кворума, даже
  при формально достаточной доле «за». Результаты видны правлению всегда,
  рядовым членам — только после закрытия голосования (чтобы не влиять на
  ещё не проголосовавших). Итоговый подписанный протокол прикрепляется
  вручную (как и у очных собраний) — не генерируется автоматически

### Мастер первоначальной настройки (`/setup`)
Для председателя — единая точка входа в заполнение системы данными на
старте, не отдельная параллельная бизнес-логика поверх уже существующих
страниц. Чек-лист из восьми шагов, статус каждого («заполнено»/«не
заполнено») считается на лету по фактическим данным в БД — отдельного
флага «мастер пройден» нет, открыть `/setup/` и дозаполнить пропущенное
можно в любой момент, не только при первом запуске. Пункт меню
«Мастер первоначальной настройки» (только для председателя) и баннер на
дашборде, пока не всё заполнено.
- **Карточка кооператива** / **расчётный счёт** / **контрагент-поставщик
  электроэнергии** / **тариф** / **счётчик кооператива и начальные
  показания** — свои короткие формы прямо в мастере (со ссылками на полные
  страницы для тонкой настройки остального)
- **Люди** и **гаражи** — быстрое добавление по одному (переиспользует
  существующие формы `persons.create`/`garages.create` без дублирования
  логики) и **импорт из CSV** с **настраиваемым форматом**: кнопка
  «Настроить формат» на каждом из двух шагов открывает попап-справочник
  всех доступных колонок (`PEOPLE_COLUMN_CATALOG`/`GARAGES_COLUMN_CATALOG`
  в `setup_wizard.py`) — председатель отмечает чекбоксом, какие колонки
  есть в его файле, и указывает их порядковый номер слева направо; состав
  и порядок сохраняются в БД (`CsvImportProfile`, по одной записи на
  «people»/«garages») и переиспользуются при следующих импортах и в
  скачиваемом образце CSV — под любую выгрузку из внешней системы (1С,
  Excel, что угодно), не только под фиксированный набор колонок «из
  коробки». Обязательные поля (ФИО — у людей; номер гаража, площадь и ФИО
  собственника — у гаражей) нельзя снять с импорта — попытка сохранить
  формат без них отклоняется. У гаражей несколько строк с одним номером
  гаража добавляют по совладельцу на строку (площадь и остальные поля
  берутся из первой встреченной строки с этим номером); собственник,
  которого нет в базе, создаётся автоматически по ФИО
- **Состав правления** — самый первый созыв создаётся без протокола общего
  собрания (`governance.create_term()` в обычном режиме требует протокол —
  на старте системы избирать было ещё не из чего, состав фиксируется как
  есть), дальше используется уже существующая страница созыва
  (`governance.term_detail`) без изменений. Отдельная кнопка «Создать
  карточку и привязать» — если у входящего в систему председателя ещё нет
  привязанной карточки `Person` (обычная ситуация для самой первой
  учётной записи из `seed.py`), иначе применение состава созыва
  (`sync_user_role`) не подействует на его собственную сессию входа

### Общее
- **Главная страница (страница входа)** — форма входа компактной карточкой
  в правом верхнем углу; по центру — новостная лента кооператива
  (`News`), редактируется правлением через `/news` (список/добавление/
  редактирование/удаление, доступ по `roles_required(RoleEnum.BOARD)`);
  видна и анонимным посетителям (страница входа — де-факто главная,
  `/` → `/dashboard` → редирект на неё для незалогиненных), и как раздел
  «Новости» в меню правления после входа. Показываются последние 5 записей.
  Текст — в упрощённой markdown-разметке (**жирный**, *курсив*,
  [ссылка](url), списки через «- », заголовок «### »; панель кнопок над
  полем ввода в форме `/news/new`, `/news/<id>/edit`) и рендерится в
  безопасный HTML через `bleach` (`app/news_format.py`). Можно прикреплять
  фото и файлы (`NewsAttachment`, множественная загрузка); на ленте на
  главной — короткое текстовое превью (400 знаков, без разметки) со
  ссылкой «Читать дальше» на полную страницу `/news/<id>` (тоже публичную)
  для длинных новостей, полностью отрендеренная новость сразу — для
  коротких; фото показываются превью-миниатюрами прямо в ленте, остальные
  файлы — списком ссылок на полной странице
- **Переключатель языка** — выпадающее меню с флагом текущего языка на
  кнопке (🇷🇺/🇬🇧, эмодзи, без внешних иконочных шрифтов), в каждом пункте
  меню — флаг + название языка
- **Переключатель темы** — одна кнопка-пиктограмма (не выпадающее меню,
  тем всего две): показывает иконку той темы, в которую переключит клик
  (луна на светлой теме — переключить на тёмную, и наоборот)
- **Баланс кооператива на дашборде** (правление/бухгалтер/председатель) —
  сумма фактических балансов всех расчётных счетов (`BankAccount.balance`,
  вносится вручную в реквизитах кооператива), считается динамически при
  каждом заходе. Это НЕ то же самое, что сумма ожидаемых поступлений по
  лицевым счетам членов (сколько кооперативу должны/переплатили) — тот
  показатель отдельно доступен как `accounting.receivables_balance()`, но
  на дашборд сейчас не выведен
- **Локализация** — русский/английский, переключатель в шапке (простой
  словарь `app/i18n.py`, без внешних зависимостей) — выпадающее меню с
  флагом; даты и суммы везде через
  `fmt_date()`/`fmt2()`, а не голым ISO/числом
- **Тема** — светлая/тёмная, хранится в сессии, переключается одной
  кнопкой-пиктограммой
- **Поиск в длинных списках выбора** — селекты с потенциально большим числом
  вариантов (собственники/контакты гаража, привязка учётной записи к
  человеку, секретарь/председательствующий на собрании, поставщик
  электроэнергии из контрагентов и т.п.) превращены в текстовое поле с
  выпадающим списком, отфильтрованным по вводу
  (`data-searchable` в шаблоне + один общий JS-компонент в `base.html`, без
  внешних библиотек — работает и для полей, добавляемых на лету, например
  строк собственников гаража)
- **Роли и доступ** — рядовой член видит только свои данные (по привязке
  учётной записи к `Person` через владение гаражом или через сам `Person`);
  правление/бухгалтер — все данные; председатель — дополнительно учётные
  записи и правка чужих ошибок (последнее показание счётчика). Списки
  «Гаражи» и «Люди» (`/garages`, `/persons`) и карточка конкретного гаража
  или человека серверно проверяют доступ (не только скрывают пункт меню) —
  рядовой член не может открыть чужой гараж или чужую карточку по прямой
  ссылке

## Что осознанно не реализовано

- **Годовые отчёты и ставки взносов** (`AnnualReport`/`FeeRate`) — дашборд
  умеет показать последний отчёт, если он есть в БД, но создать его через
  UI нельзя (только напрямую в БД)
- **«Скачать PDF» для платёжки по электричеству гаража** — путь
  `/pd4/print/pdf` пока рассчитан только на счета членов кооператива

## Известные ограничения

- Код синтаксически проверяется в каждой сессии (`py_compile` + Jinja2-
  парсинг всех шаблонов + статическая сверка всех `url_for(...)` с
  реальными маршрутами + сверка всех русских строк со словарём переводов в
  `i18n.py`), и дополнительно end-to-end через `app.create_app()` под
  реальным Flask/SQLAlchemy/Alembic/weasyprint — сеть и зависимости в
  песочнице для этого есть. Ключевые бизнес-сценарии (гараж → собственники
  с долями → показания → начисление → платёж с частичным/полным закрытием
  долга → печать ПД-4 с QR; миграции на БД с реальными данными; расчёты с
  контрагентами включая частичную оплату, правку и сторно платежа) регулярно
  прогоняются реальными HTTP-запросами через `app.test_client()` при каждом
  изменении, но это не формальный набор автотестов (`pytest` и т.п.) — при
  доработках стоит по-прежнему проверять вручную сценарии, которые
  затрагивает конкретное изменение.
- Подробная история изменений по сессиям (что именно менялось в моделях,
  зачем и какие миграции для этого нужны) — в `context.md` рядом с этим
  файлом; он предназначен для следующей сессии продолжения работы над
  проектом, но может быть полезен и как changelog.
- **Загрузка ключевой ставки ЦБ РФ с cbr.ru не проверялась вживую** — сайт
  cbr.ru недоступен из песочницы, где ведётся разработка. Запрос к
  официальному SOAP-сервису собран по документированному формату и
  парсер проверен на синтетическом ответе того же формата, но при первом
  реальном использовании стоит один раз проверить кнопку «Загрузить с
  cbr.ru» на странице «Пеня» — если формат ответа окажется другим, есть
  запасной вариант: внести ставку вручную (там же, в той же форме).
- **Пеня и задним числом внесённые платежи** — если платёж вносится
  позже, чем по соответствующим дням уже была посчитана и начислена
  пеня, пересчёт это не отменяет и не исправляет — досчитывает только
  новые дни вперёд. Если нужно исправить уже начисленную пеню, начисление
  на счёте пени придётся скорректировать вручную.

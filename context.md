# Архитектурные принципы и грабли

**FIFO-разнесение платежей**: `accounting._reallocate_fifo(charges, payments)`
— общий механизм для гаражей и счетов членов. Обёртки:
`reallocate_garage_charges(garage)`, `reallocate_member_charges(account)`.
Вызывать после ЛЮБОГО создания `Charge`/`Payment` — не автоматически.
Идемпотентна (пересчитывает с нуля). `balance()` от `ChargeAllocation` не
зависит — отдельный агрегат для остатка конкретного начисления (пеня,
статусы в журнале).

**CSV-импорт в мастере — настраиваемый формат**: `CsvImportProfile` (по
записи на «people»/«garages»), `columns` — JSON-список ключей в порядке
файла председателя, хранится в БД (переиспользуется между импортами). UI —
попап: чекбокс (есть/нет) + числовое поле позиции на каждую колонку
каталога, без drag-and-drop. Обязательные колонки — чекбокс `disabled` +
скрытое поле-дублёр (иначе браузер не отправит значение выключенного
чекбокса). Парсинг — `dict(zip(columns, cells))`, код обращается по ключу
(`values.get("full_name")`), не по позиции. Детект заголовка —
`_looks_like_header_row()` проверяет совпадение ЛЮБОЙ ячейки первой строки
с подписью любой колонки каталога (не только первой ячейки). CSV: запятая,
UTF-8 (`utf-8-sig`), точка как десятичный разделитель (не запятая — не
путать с разделителем колонок). Импорт гаражей идемпотентен по номеру
гаража + паре (гараж, человек).

**Мастер настройки (`/setup`, председатель)**: где уже есть полноценная
страница (гараж, состав правления) — мастер только даёт точку входа, не
дублирует логику своими формами; свои формы — только для CSV-импорта и
коротких форм присвоения полей (кооператив/счёт/тариф/поставщик/счётчик).
Статус шага — вычисляется по данным (`wizard_status()`), не персистентный
флаг. Первый созыв правления — `setup_wizard.board_init()` создаёт
`BoardTerm` с `elected_by_meeting_id=None` напрямую (обычный
`governance.create_term()` требует протокол — на первом запуске протокола
физически не было). **Грабли**: председатель из `seed.py` создан с
`person_id=None` — `sync_user_role()` не находит `User` по `person_id` при
применении состава; `board_link_me()` — быстрая привязка на шаге.

**Новости** (`news_format.py`, `NewsAttachment`): упрощённый markdown →
`bleach.clean()` (без `img`/`script` — картинки отдельно через вложения) →
`bleach.linkify()`. Превью ленты (`excerpt()`) — отдельный проход через
`plain_text()`, НЕ обрезка уже отрендеренного HTML (риск порвать тег).

**Alembic — история сброшена до одной baseline-ревизии** (сделано по
просьбе, пока не было боевых данных — допустимо ТОЛЬКО в этом состоянии,
не после первого боевого использования).

**Пеня**: непогашенный остаток × ключевая ставка ЦБ × 1/300 (первые 30
дней) / 1/150 (с 31-го) × дни, посуточно. Считается на лету при каждом
открытии `/dashboard`/`/finance/penalty/` (`accrue_penalties`, без flash),
дёшево за счёт `Charge.penalty_calculated_through`. Персистентные
`Charge`-записи нужны (иначе нечем платить/печатать в ПД-4), не виртуальное
число. **Ограничение**: платёж задним числом после того, как пеня уже
посчитана за эти дни — пересчёт не отменяет, только продолжает вперёд;
ретроактивной коррекции нет.

**cbr.ru (ключевая ставка)** — SOAP `DailyInfoWebServ/DailyInfo.asmx`,
метод `KeyRate`, отдаёт запись на каждый календарный день (не только на
даты изменений) — сжимается `penalty._compress_to_change_points()` (на
входе) и `penalty.compact_key_rates()` (проход по истории). `is_manual=True`
записи не трогаются. Ответ — вложенные XML-элементы (diffgram), НЕ
экранированная строка; парсер ищет `DT`+`Rate` по всему дереву без
namespace. **НЕ ПОДТВЕРЖДЕНО живым тестом** (домен недоступен из
песочницы) — если таблица не заполняется после реального похода на
`DailyInfo.asmx`, проверять здесь первым делом.

**Права доступа** — только через `permissions.py`
(`is_board()`/`is_chairman()`/`is_privileged()`/`is_owner_or_board()`/
`can_view_member_account()`), пробрасываются в Jinja через
`app/__init__.py:_inject_user()`. **Грабли с затенением** (встречалась
дважды: `garages/detail.html`, `pd4.select()`): НЕ передавать
`is_board=is_board()` кwarg'ом в шаблон — `{% include %}` передаёт
контекст целиком, внутри инклюда вызов `is_board()` получает bool →
`TypeError`. Ловится только e2e-рендером, не статическим парсингом; широкий
smoke-тест по ролям должен реально включать ВСЕ блюпринты (баг в `/pd4/`
пролежал необнаруженным несколько сессий именно поэтому).

`roles_required`/`ROLE_LEVEL` (`auth.py`) — доступ к роуту целиком
(декоратор, при отказе редирект на `/dashboard` с flash, НЕ сырой 403).
`permissions.py` — доступ к конкретному объекту внутри уже открытого
роута. Разные уровни, не путать.

**Правление** — `governance.apply_term()` применяет состав явной кнопкой,
не автоматически при добавлении членов (иначе председатель рискует
потерять свой флаг на середине заполнения состава). Бухгалтер — НЕ через
созыв, назначается председателем напрямую, применяется сразу (риска
самоблокировки нет).

**Searchable select**: выпадающий список — прямой потомок `document.body`,
`position:fixed` (координаты от `getBoundingClientRect()`), НЕ внутри
обёртки поля — иначе `modal-dialog-scrollable` (`overflow-y:auto` на
`.modal-body`) обрезает его независимо от z-index. Прячется на
`hidden.bs.modal`. `window.enhanceSearchableSelect` — глобальная, вызывать
вручную для динамически добавляемых `<select>`.

**Alembic + SQLite**: batch-mode обязателен для ALTER; `naming_convention`
на `Base.metadata` даёт имена FK-констрейнтам автоматически.
`ADD COLUMN NOT NULL` без дефолта падает на существующих строках — нужен
`server_default=...`, дописывать руками. `DROP COLUMN` в batch-режиме имени
констрейнта не требует. При расхождении веток — перебазировать линейно, не
merge-ревизию с двумя `down_revision`. Каждая миграция — цикл
`upgrade head → alembic check → downgrade → upgrade head` на БД с реальными
данными в таблицах, не только на пустой схеме.

**Прочее**: `cooperative_balance()` (реальные деньги, сумма
`BankAccount.balance`) ≠ `receivables_balance()` (сумма лицевых счетов
членов) — не путать. Сводка балансов на странице гаража фильтруется через
`can_view_member_account()` в роуте (Python), не в шаблоне. Модалки —
`modal-lg` по умолчанию. Верификация после каждой правки: `py_compile`,
Jinja-парсинг, статическая сверка `url_for`, AST-проверка дублей ключей
`i18n.py`, и обязательно e2e через `test_client()` под разными ролями —
статический разбор не ловит затенение переменных/неверные дефолты роутов.

**Электронное голосование**: вес голоса человека = сумма его
`GarageOwnership.share` по ВСЕМ гаражам (`voting.person_voting_weight`), не
бюллетень «на гараж» — `VoteBallot` на (question, person), не (question,
garage, person). **Кворум — жёсткое правило**: > 50% от общего веса
кооператива (`QUORUM_THRESHOLD=0.5`, `total_cooperative_weight()`), не
настраиваемое поле. Порог принятия по вопросу
(`VoteQuestion.majority_threshold`, настраиваемый) считается ВСЕГДА от
общего числа голосов кооператива, не от числа проголосовавших — один
знаменатель в системе, `question_results()` дополнительно проверяет
`quorum_met()`. Статусы: draft → open (upsert по question_id+person_id,
переголосование разрешено) → closed (явная кнопка ИЛИ истечение
`closes_at`). Протокол — обычный `Document`, не автогенерируется. Права:
управление — только председатель; черновики видны только правлению;
результаты по вопросам — рядовым членам только после закрытия. Голосовать
может только человек с весом > 0.

**Крон-скрипт ключевой ставки**: `scripts/update_key_rate.py` — standalone
(`create_app()`+`app_context()`), не через Flask-роут, использует
`fetch_key_rates_from_cbr`/`save_key_rates`/`compact_key_rates` из
`penalty.py`. `.sh`-обёртка — лог в `instance/logs/`, `flock`, автоопределение
venv. Тот же паттерн — `scripts/poll_ewelink.py` (см. п. 29 ниже).

**Права на печать ПД-4** — разделены по видам платёжек, не по ролям
целиком: правление печатает ТОЛЬКО взносы (MemberAccount); электричество
(PersonalAccount на гараж) правление печатать не может вообще, даже
подставив garage_id вручную — всегда требуется реальное владение гаражом.
Рядовой член печатает оба вида по своим гаражам,
`pd4._collect_member_debts()` агрегирует их в одном вызове,
`_build_mixed_slips()` строит слипы вперемешку через адаптер
`_electricity_account_view()`. Электричество выставляется НА ГАРАЖ целиком
(общий счётчик) — частичный собственник видит и может оплатить весь
остаток, не только свою долю (в отличие от взносов). Кнопка «Назад к
выбору» — видна только правлению (`is_board()`, было завязано на флаг
`electricity`).

**API банка (`app/bank_api/`, `app/bank_sync.py`)** — реализован только
Сбербанк (`BankAccount.api_provider`: none/sberbank/vtb/tbank, для
ВТБ/Т-Банк `get_client()` всегда `None`). Всё ниже подтверждено реальным
тестированием кооперативом, не предугадано заранее:
- Авторизация — access_token (60 мин, не хранится) + refresh_token (180
  дней, `BankApiCredential.refresh_token_encrypted`), НЕ client_credentials.
  Банк может ротировать refresh_token при обновлении —
  `SberbankClient.rotated_refresh_token` + `_persist_rotated_refresh_token`
  ОБЯЗАТЕЛЬНО вызывать в каждом роуте с `get_client()`, включая путь
  ошибки (refresh мог пройти даже если бизнес-запрос упал) — забытый роут
  тихо ломает токен при следующей ротации.
- mTLS обязателен для TLS-соединения, не только токен в заголовке.
  Клиентский сертификат — .pfx/.p12, конвертируется в PEM
  (`cryptography.pkcs12`), хранится в `BANK_CERTS_FOLDER` (не
  `UPLOAD_FOLDER` — там есть отдающий роут), права 0o700/0o600. .pfx и
  пароль не сохраняются. **Личный кабинет генерирует .p12 с ЦЕПОЧКОЙ
  сертификатов** — `_save_client_cert` сохраняет всю цепочку
  (`extra_certs`), не только лист.
- Доверенные корни — УЦ Сбера И НУЦ Минцифры (обе, подтверждено
  developers.sber.ru/docs/ru/sber-api/start/tls) — обычный
  requests/certifi-бандл их не знает. Готовые архивы по прямым ссылкам от
  банка (`Config.SBERBANK_API_CA_BUNDLE`, `.env.example`), не собирать
  вручную с госуслуг.
- Тестовый контур — `https://fintech-test.sberbank.ru:9443` (подтверждено
  из личного кабинета кооператива), НЕ `edupirfintech.sberbank.ru`.
  `token_url` выводится ИЗ `base_url`, не захардкожен на промышленный хост.
- Официальный перечень scope-операций НЕ содержит явной операции для
  реестра начислений (`PAYMENTS_REGISTRY` для платежей есть) — не
  проверено на практике, возможно отдельный продукт; ручной путь
  (веб-интерфейс СберБизнес Онлайн) не зависит от API и всегда доступен.
- Реестры — CP1251-текстовый файл (не JSON), формат НАСТРАИВАЕМЫЙ
  (`BankRegistryFormat`, тот же принцип что CSV-импорт,
  `bank_api/registry_file.py: CHARGE_FIELD_CATALOG/PAYMENT_FIELD_CATALOG`).
  Дефолт — реальный формат по образцам от председателя: начисления — 5
  полей, точка как разделитель, без заголовка; платежи — 13 полей, запятая
  как разделитель, завершающая строка-сводка (`trailer_prefix`,
  распознаётся и пропускается). Сумма начисления (`.amount`, FIFO) и сумма
  зачисления (`.credited_amount`/`.fee_amount`, за вычетом комиссии банка)
  — РАЗНЫЕ поля, не путать. `build_registry_format()` — единое место
  сборки формата из БД для API и ручного скачивания/загрузки.
- Реестр начислений строится из ТЕКУЩЕЙ задолженности (`balance() < 0`),
  не из `Charge` за период — известное ограничение: нет отслеживания «уже
  в реестре», повторная отправка шлёт всё заново (дублей у кооператива не
  создаёт, это витрина для банка).
- Выписка тоже гасит долг автоматически (не только реестр платежей):
  `extract_account_number()` (регэксп `лс\s*[:№]?\s*(\d+)`) распознаёт
  номер лицевого счёта в тексте назначения; при совпадении зачисление
  (не списание) заводит `Payment` на ПОЛНУЮ сумму и разносит по FIFO без
  подтверждения. Комиссия банка в выписке отдельным полем не приходит (в
  отличие от файла реестра) — вся зачисленная сумма и есть гашение.
- Если номера нет — поиск по ФИО (`_resolve_account_by_name`): точное
  совпадение `Person.full_name`, либо форма «Фамилия И.О.» (банк часто
  указывает того, ЗА кого платят, не плательщика), включая
  `GarageContact` (поднимает счета владельцев его гаража). Разносится
  ТОЛЬКО при однозначном результате; при нескольких кандидатах — сужение
  по `FeeType.name` в тексте (`_narrow_by_fee_type`), иначе остаётся
  неразнесённым. Общий путь для выписки и реестра —
  `_allocate_payment_to_account()`.
- **Вся банковская интеграция не проверялась живым запросом до тестового
  подключения кооперативом** (домен недоступен из песочницы разработки) —
  всё выше уже прошло через реальное тестирование и исправлено; заново
  ничего непроверенного не осталось, кроме scope-операции реестра
  начислений (см. выше).

**Мониторинг электроэнергии по фазам — eWeLink POWCT** (новая подсистема,
первая версия, ЕЩЁ НЕ ПРОВЕРЕНА живым тестом). Отдельно от
`app/power.py` (помесячный биллинг) — здесь автоснимок мощности/
напряжения/тока раз в минуту, без начислений. Модели: `EWeLinkAccount`
(singleton, секреты/токены через `app.bank_api.crypto` — переиспользован,
не продублирован), `PowerPhaseDevice` (фаза A/B/C ↔ `deviceid`),
`PowerPhaseReading` (`raw_params` хранит сырой JSON, пока поля не
подтверждены). Клиент `app/ewelink/client.py` — **сознательно
неофициальный** вход email/пароль (как Home Assistant SonoffLAN), не
официальный OAuth2 Open API (модерация заявки до нескольких дней —
отклонено явно при постановке задачи). Blueprint
`app/electricity_monitor.py` (`/electricity/`) — просмотр правлению,
настройки/устройства только председателю. Опрос —
`scripts/poll_ewelink.py`+`.sh` по образцу `update_key_rate`, cron раз в
минуту, не APScheduler. Тесты (`test_electricity_monitor.py`, 17 шт.) —
целиком на monkeypatch-клиенте, как `SberbankClient` в `test_bank_sync.py`.
Попутно исправлен предсуществующий баг разметки в
`cooperative/payment_registry.html` (`{% for %}...{% else %}` был закрыт
`{% endif %}` вместо `{% endfor %}` — шаблон не парсился).

**НЕ ПОДТВЕРЖДЕНО живым тестом** (устройства заказчика: `10023349b3`,
`1002334597`, `1002333baf`) — при первом реальном запуске обязательно
проверить и зафиксировать здесь:
1. хост региона (`REGION_HOSTS` в `client.py`, вероятно `eu`, но домены apia/api меняются);
2. путь/формат тела запроса обновления токена (`/v2/user/refresh` — минимум два варианта у разных открытых клиентов);
3. точные имена полей `params` POWCT — код пробует `power`/`voltage`/`current` и `power_00`/`voltage_00`/`current_00` (`POWER_KEYS` и т.п.), неизвестно, домножены ли voltage/current на 100;
4. коды ошибок 401/402 как признак протухшего токена — тоже из открытых клиентов, не из официальной документации.


# Хронология сессий (сжато)

1. Вкладки «Электричество»/«Счёт» гаража объединены, с реальным зачётом FIFO.
2. ПД-4 для электросчёта — печать долга по общему счётчику.
3. FIFO-разнесение платежей введено впервые (гаражи/электричество).
4. Один платёж — одна строка в журнале начислений.
5. Валидация показаний счётчика — запрет ввода меньше предыдущего.
6. Аудит доступа — закрыты реальные дыры (чужие `/persons/<id>` и т.п.).
7. Баланс кооператива = сумма расчётных счетов, не сумма ожидаемых поступлений.
8. Права доступа централизованы в `permissions.py` (было продублировано).
9. Расчётные счета/баланс/комментарий кооператива скрыты от рядовых членов.
10. Созывы правления + ревизионная комиссия — `BoardTerm`/`BoardMember`.
11. Старые чекбоксы флагов правления на карточке человека убраны.
12. Бухгалтер отделён от созыва правления — назначается председателем напрямую.
13. Автоматическое начисление пени — новый модуль `penalty.py`.
14. Слияние параллельных веток (пеня + рефакторинг бухгалтера).
15. Точечные правки после слияния (баланс кооператива на `/cooperative/`).
16. Электронное голосование (очно-заочное/заочное) + крон-скрипт ставки ЦБ.
17. Права на печать ПД-4 пересмотрены: правление — только взносы.
18. Главная страница переработана: форма входа в компактную область.

### Доработка: связь показаний и начислений перенесена на уровень БД (не только вёрстки)
Первая версия объединённой таблицы сопоставляла показания и платежи чисто позиционно через `itertools.zip_longest(readings, payments)` — по порядковому номеру в двух независимо отсортированных списках, без реальной связи в данных. По просьбе — заменено на настоящую связь в БД:
- **models.py**: `ElectricityReading` получила поле `tariff` (Numeric(10,4)) — тариф ₽/кВт·ч, применённый при расчёте `amount` именно для этого показания (фиксируется в момент внесения, не пересчитывается задним числом при последующих изменениях тарифа). `Charge` получила FK `reading_id → electricity_reading.id` (`ondelete="SET NULL"`, индексирован) и relationship `reading` (`back_populates="charge"`); у `ElectricityReading` — обратная связь `charge` (`uselist=False`, один к одному). Раньше начисление, созданное по показанию, было связано с ним только текстом в комментарии ("Начислено по показаниям от {date}") — теперь это настоящий внешний ключ.
- **garages.py, `add_electricity_reading()`**: при внесении показания теперь `db_session.flush()` сразу после `add(reading)`, чтобы получить `reading.id`; начисление создаётся с `reading_id=reading.id`; тариф сохраняется в `reading.tariff` независимо от того, посчиталась сумма или нет.
- **garages.py, `detail()`**: `ledger_rows` строится заново без `zip_longest` — каждое показание берёт своё начисление через `r.charge` (реальная связь), плюс отдельными строками добавлены ручные начисления без привязки к показанию (`c.reading_id is None`, любой вид взноса — с меткой вида в скобках) и платежи; всё сортируется по фактической дате (`sort_date`) от новых к старым. Убран неиспользуемый импорт `itertools.zip_longest`.
- **⚠️ Требуется пересоздание БД** при следующем запуске (`rm instance/coop.db && python seed.py`) — `Base.metadata.create_all()` не добавляет новые колонки/FK к уже существующим таблицам (в проекте нет Alembic, см. существующий "нюанс" в этом файле про смену enum DocumentType).
- Отдельная таблица "Платежи" на вкладке убрана из вёрстки; её данные (`charges`/`payments`/`fee_types`) по-прежнему передаются в шаблон из `detail()` на случай будущих доработок.

### Кнопка оплаты → /pd4/print
- Новая последняя колонка в таблице — иконка 💳 "Оплатить", показывается только если по счёту есть задолженность (баланс < 0).
  - Для member-счетов: `url_for('pd4.print_slips', account_id=acc.id)`.
  - Для электросчёта: `url_for('pd4.print_slips', garage_id=o.garage.id)`.
- `pd4.py: print_slips()` — расширен: `garage_id` в query/form → печать по электросчёту гаража (см. ниже); `account_id` в GET query → печать по одному конкретному member-счёту (раньше GET без параметров печатал сразу вообще все долги пользователя — так и осталось как поведение по умолчанию, если `account_id`/`garage_id` не переданы).
- Новая функция `pd4._print_electricity_slip(garage_id)` — доступ: правление или текущие собственники этого гаража; берёт `garage.account`, считает долг через `accounting.balance(garage)`, строит QR через новую `accounting.pd4_qr_payload_electricity()`, сохраняет `PD4Document`, рендерит `pd4/print.html`.
- **models.py, `PD4Document`**: добавлено поле `personal_account_id` (FK → `personal_account.id`, `ondelete="SET NULL"`) как альтернатива существующему `account_id` (FK → `member_account.id`), по образцу уже имеющегося в `Charge` паттерна `garage_id`/`account_id` — `CheckConstraint` `ck_pd4_document_target` требует ровно одно из двух. **Требует пересоздания БД** (см. предыдущую заметку про `rm instance/coop.db && python seed.py`).
- **accounting.py**: новая `pd4_qr_payload_electricity(coop, bank_account, garage, personal_account, amount)` — тот же формат ГОСТ Р 56042-2014, что и `pd4_qr_payload()`, но т.к. электросчёт общий на гараж (не привязан к конкретному человеку), поле "ФИО плательщика" — все текущие собственники гаража через запятую; "Назначение платежа" берёт название вида взноса из `FeeType` с `code="electricity"` (или "Электроэнергия", если такого вида нет).
- **pd4/print.html**: рендерит электрослип через лёгкий duck-typed адаптер `pd4._electricity_account_view()` (`type(...)`, по образцу уже использовавшегося в `cabinet.profile()` для pending-ревизий) — подставляет `.account_number/.person.full_name/.fee_type.name/.garage` под тот же интерфейс, что и `MemberAccount`, чтобы не трогать разметку квитанции. Кнопки "Скачать PDF" и "Назад к выбору" скрыты для электрослипов (флаг `electricity=True` в шаблоне) — путь `/pd4/print/pdf` пока рассчитан только на `MemberAccount` и не адаптирован под электросчета.

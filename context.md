# Архитектурные принципы и грабли

## FIFO-разнесение платежей (ChargeAllocation)
Единый механизм для гаражей (электричество) и счетов членов (взносы/пеня):
`accounting._reallocate_fifo(charges, payments)` — общая механика, старые
начисления закрываются старыми платежами. Обёртки: `reallocate_garage_charges(garage)`,
`reallocate_member_charges(account)`. Вызывается после ЛЮБОГО добавления
`Charge`/`Payment` на затронутый объект — если добавляешь новую точку
создания начисления/платежа, не забыть вызвать. Идемпотентна (пересчитывает
с нуля), поэтому безопасна для повторного вызова. `balance()` (агрегатная
сумма) от `ChargeAllocation` не зависит — используется отдельно везде, где
нужен точный остаток конкретного начисления по датам (пеня, статусы
«оплачено/частично/не оплачено» в журнале начислений).

## CSV-импорт в мастере — настраиваемый формат, не жёсткий порядок колонок
Изначально формат CSV для импорта людей/гаражей был жёстко зашит (позиция
в строке = конкретное поле). По прямой просьбе переделано на настраиваемый:
`CsvImportProfile` — по одной записи на тип импорта («people»/«garages»),
`columns` — JSON-список ключей колонок в порядке файла председателя,
сохраняется и переиспользуется, а не задаётся заново при каждом импорте
(«вдруг ещё пригодится» — прямая цитата из запроса, отсюда и решение
хранить в БД, а не как одноразовый параметр формы импорта).

**UI — попап со списком колонок и позицией, не drag-and-drop.** Каждая
колонка каталога — чекбокс (есть/нет в файле) + числовое поле (её позиция
слева направо, начиная с 1). Осознанно не реализовывался drag-and-drop
реордеринг (тянуть элементы списка мышью) — числовое поле для позиции
даёт тот же результат (свободный порядок), но без JS-библиотек и без
рисков потерять состояние при случайном клике мимо; полностью работает
и без JavaScript (graceful degradation — хотя в проекте это не жёсткое
требование, раз Bootstrap-модалки и так на JS). Обязательные колонки
(ФИО — у людей; номер, площадь, ФИО собственника — у гаражей) рендерятся
с чекбоксом `disabled` (визуально нельзя снять) + скрытым полем с тем же
именем — раз чекбокс задизейблен, браузер не отправит его значение в
форме, а скрытое поле гарантирует, что колонка всё равно попадёт в
список выбранных при сохранении.

**Парсинг под любой порядок — dict вместо позиционной распаковки.**
`_get_import_columns()` отдаёт активный (сохранённый, либо дефолтный —
полный каталог по порядку, как было раньше жёстко) список ключей; при
чтении каждой строки CSV делается `dict(zip(columns, cells))`, и дальше
код работает с `values.get("full_name")` вместо `cells[0]` — сам импорт
не завязан на то, что конкретное поле стоит на конкретной позиции.
Скачиваемый образец CSV (`_build_template_csv`) строится по тому же
активному формату — шапка и пример всегда синхронны с тем, что реально
ожидает импорт.

**Детект строки-заголовка — тоже больше не завязан на позицию.**
Раньше проверялась только первая ячейка на конкретное имя («ФИО» или
«Номер гаража») — с настраиваемым форматом первая колонка может быть
любой. `_looks_like_header_row()` проверяет, совпадает ли ХОТЬ ОДНА
ячейка первой строки (без учёта регистра) с подписью любой колонки
каталога — не идеально строго, но безопасно: реальные ФИО/номера/адреса
практически никогда буквально не совпадают с текстом подписи колонки.

## Мастер первоначальной настройки — оркестрация, не дублирование
`app/setup_wizard.py` (`/setup`, только председатель). Ключевое архитектурное
решение: там, где уже есть полноценная страница с бизнес-логикой (гараж с
собственниками — `garages.create`, состав правления — `governance.term_detail`),
мастер НЕ переписывает эту логику своими формами — только даёт точку входа
(ссылку, либо в случае состава правления — недостающий bootstrap-путь) и
дальше отдаёт управление существующей странице. Свои формы у мастера — только
для того, чего раньше не было вообще ни в каком виде: импорт людей/гаражей
из CSV, и короткие формы для карточки кооператива/счёта/тарифа/поставщика/
счётчика (это просто присвоение полей модели, не бизнес-логика, дублирование
здесь дешёвое и не рискованное).

**Статус шага — не персистентный флаг, а вычисление по данным** (тот же
принцип, что и `receivables_balance()`/`cooperative_balance()` — см. ниже):
`wizard_status()` каждый раз проверяет напрямую (`Cooperative.inn` заполнен,
`BankAccount` есть хоть один, `ElectricitySettings.supplier_id` задан,
и т.д.). Из-за этого мастер можно открывать сколько угодно раз, в любом
порядке шагов, без риска рассинхронизации «флага» с реальными данными.

**Первый созыв правления — специально без протокола общего собрания.**
`governance.create_term()` в обычном режиме требует `elected_by_meeting_id`
(это осознанное ограничение, не грабли — переизбрание без протокола было бы
дырой). На самом первом запуске протокола просто ещё физически не было —
избирать было не из чего, состав фиксируется «как есть». Поэтому
`setup_wizard.board_init()` — отдельный маршрут, создающий `BoardTerm` с
`elected_by_meeting_id=None` напрямую (не переиспользует `create_term()`),
и сразу редиректит в существующий `governance.term_detail` — добавление
членов и применение состава (`apply_term()`) дальше идёт через уже
работающий интерфейс без единой новой строчки кода для этой части.

**Грабли: председатель из `seed.py` не привязан к `Person`.** Первая
учётная запись создаётся с `person_id=None` (человека с таким ФИО ещё нет).
Без привязки `sync_user_role()` при применении состава созыва не находит
`User` по `person_id=person.id` и не меняет роль ЭТОЙ сессии входа — только
у новых учётных записей. `setup_wizard.board_link_me()` — быстрая привязка
прямо на шаге правления (создаёт `Person`, проставляет `g.user.person_id`),
чтобы не уходить отдельно в «Учётные записи» на первом шаге настройки.

**CSV — простой формат, без хитрого парсинга.** Запятая как разделитель
(не `;`), UTF-8 (с допуском BOM — `utf-8-sig`), первая строка — заголовок
(определяется по первой ячейке и пропускается, не парсится). Числа — только
с точкой, не с запятой (чтобы не путать с разделителем колонок при
экспорте из Excel с русской локалью — явно задокументировано на странице
шага, не пытаться угадывать десятичный разделитель автоматически). Гаражи:
несколько строк с одинаковым номером гаража = несколько собственников
(площадь и остальные поля берутся из первой встреченной строки с этим
номером); отсутствующий в базе собственник создаётся по ФИО автоматически
(`_find_or_create_person_by_name`, точное совпадение без учёта регистра).
Импорт идемпотентен для повторного запуска: существующие гаражи по номеру и
существующие связи владения по паре (гараж, человек) не дублируются, только
обновляют долю.

## Новости — markdown + вложения, объединено из параллельной сессии
Функциональность (`app/news_format.py`, `NewsAttachment`, `/news/<id>`
публичная страница, панель форматирования в форме) разрабатывалась в
ДРУГОЙ сессии параллельно с мастером первоначальной настройки (см. ниже) —
пришла отдельным архивом и объединялась вручную, файл за файлом, не через
`git merge` (в проекте нет git, только последовательные архивы). Единственный
настоящий конфликт — `auth/login.html`: сторонняя сессия начала работу от
более старой версии этого файла (без выпадающего меню языка/иконки темы
из принципа «UI приведён к единому стилю» выше) и, добавляя вёрстку
превью/вложений, случайно отменила эту более позднюю правку. Разрешено
руками: взят актуальный (с выпадающим меню/иконкой) `login.html`, в него
точечно добавлены только новые куски вёрстки (excerpt, вложения-миниатюры,
ссылка «Читать дальше»), а не файл целиком одной из сторон.
`app/news.py`, `models.py` (класс `NewsAttachment`), `i18n.py` (новые
ключи), `app/__init__.py` (регистрация `render_news_html`/`news_excerpt`
как jinja-globals) — конфликтов не было, эти файлы либо не менялись второй
сессией параллельно (`models.py`/`__init__.py`/`i18n.py` — только
добавления, без пересечения строк с правками мастера), либо (`news.py`,
`news/list.html`, `news/form.html`) были нетронуты в этой сессии вообще —
скопированы из другой ветки как есть.

**Формат**: упрощённый markdown (`Markdown` + `nl2br`-расширение) →
`bleach.clean()` с явным белым списком тегов (без `img`, без `script` —
изображения новости идут отдельным каналом через `NewsAttachment`, не
встраиваются в текст) → `bleach.linkify()`. Превью для ленты
(`news_format.excerpt()`) — это ПОЛНОСТЬЮ отдельный проход через
`plain_text()` (markdown → HTML → strip тегов), не обрезка уже
отрендеренного HTML: обрезка HTML-строки по количеству символов рискует
разорвать тег или незакрыть его.

## Alembic — сброс истории миграций до одной baseline-ревизии
По прямой просьбе (проект ещё не разворачивался на боевых данных
кооператива — делать это допустимо только пока это так, не после первого
боевого использования): все 10 накопленных файлов миграций удалены,
`alembic revision --autogenerate` против пустой БД сгенерировал одну новую
`baseline current db schema`, описывающую `app/models.py` как он есть
сейчас целиком. Проверено циклом `upgrade head → alembic check (без
диффа) → downgrade base → upgrade head` — раньше этот цикл проверялся на
БД с реальными данными в таблицах (см. принцип ниже), здесь смысла нет:
это первая и единственная миграция, откатывать её всегда означает откат
в пустую схему.


Формула — сумма непогашенного остатка × ключевая ставка ЦБ РФ (на день) ×
1/300 (первые 30 дней просрочки) / 1/150 (с 31-го) × дни, посуточно, с
учётом реальных дат платежей (через `ChargeAllocation` выше). Считается на
лету при каждом открытии `/dashboard` и `/finance/penalty/`
(`accrue_penalties(today)`, без flash) — председателю ничего нажимать не
надо. Экономически дёшево: `Charge.penalty_calculated_through` делает
повторный вызов почти no-op. Персистентные `Charge`-записи на счёте-пени
всё равно нужны, а не чисто виртуальное число — иначе члену нечем платить
(платёж всегда разносится FIFO на конкретную запись) и нечего печатать в
ПД-4. Кнопка «Пересчитать на дату» осталась — для пересчёта на прошлую
дату (отчёты/печать), не как обязательный шаг.
**Известное ограничение**: если платёж вносится задним числом уже ПОСЛЕ
того, как за эти дни посчитана пеня — пересчёт это не отменяет, только
продолжает считать вперёд. Ретроактивная коррекция не реализована.

## cbr.ru (ключевая ставка) отдаёт daily-дамп, не список изменений
Официальный SOAP `DailyInfoWebServ/DailyInfo.asmx`, метод `KeyRate` — по
записи на КАЖДЫЙ календарный день диапазона, а не только на даты
изменений. Сжимается в двух местах: `penalty._compress_to_change_points()`
на входе (до записи в БД) и `penalty.compact_key_rates()` — отдельный
проход по уже сохранённой истории (для старого мусора и швов между
загрузками). Записи `is_manual=True` никогда не сжимаются/не удаляются.
Ответ ASMX сериализует `DataSet` как настоящие вложенные XML-элементы
(diffgram), НЕ как экранированную строку — парсер ищет по всему дереву
элементы с дочерними `DT`+`Rate`, без привязки к namespace. **Разбор
живого ответа cbr.ru ни разу не тестировался в песочнице** (домен
недоступен инструментам) — если после реального похода на `DailyInfo.asmx`
таблица ставок не заполняется, первым делом проверять здесь.

## Права доступа — только через permissions.py, включая шаблоны
`is_board()`/`is_chairman()`/`is_privileged()`/`is_owner_or_board()`/
`can_view_member_account()` — единственное место проверки ролей, не
дублировать. Все три первые пробрасываются в Jinja через
`app/__init__.py: _inject_user()` — в шаблонах вызывать `is_board()` и
т.п., НЕ писать `current_user.role.value == 'chairman'` вручную.
**Грабли с затенением**: НЕ кэшировать `is_board()` в локальную
Jinja-переменную с тем же именем (`{% set is_board = is_board() %}`) —
`{% include %}` передаёт родительский контекст целиком, и внутри
инклюда `is_board()`-вызов (ожидающий функцию) получит bool →
`TypeError: 'bool' object is not callable`. Ловится только реальным
рендером страницы, не статическим Jinja-парсингом. Проверять права
изменениями кода стоит e2e-рендером под разными ролями, а не только
`jinja_env.get_template()`.

## roles_required (auth.py) vs permissions.py — разные уровни
`roles_required`/`ROLE_LEVEL` в `auth.py` — доступ к роуту целиком по
минимальной роли (декоратор). `permissions.py` — доступ к конкретному
объекту внутри уже открытого роута (свой это гараж/счёт или нет).

## Правление — созыв применяется отдельной явной кнопкой
`governance.py: apply_term()` пересчитывает флаги/роли по составу созыва —
НЕ происходит автоматически при добавлении членов в состав. Если бы
происходило сразу, председатель, добавляющий состав по одному человеку,
рисковал бы потерять флаг председателя у себя самого на середине
заполнения (роль читается из БД на каждый запрос) и лишиться доступа к
странице. Разделение редактирования состава и применения прав убирает
этот риск. Бухгалтер — НЕ через созыв: назначается председателем напрямую
(`/governance/accountant/set|unset`), может не быть членом правления
вообще (аутсорс), применяется сразу (не пара действий, риска самоблокировки
тут нет).

## Searchable select — рендерится в <body>, не внутри формы
`base.html: enhanceSearchableSelect()` — общий JS для всех
`<select data-searchable>`. Выпадающий список рендерится как прямой
потомок `document.body` с `position: fixed` (координаты от
`input.getBoundingClientRect()`, пересчитываются на scroll/resize), а НЕ
внутри `position-relative`-обёртки поля. Причина: часть модалок использует
`modal-dialog-scrollable` → Bootstrap ставит `overflow-y:auto` на
`.modal-body`, что обрезает любой абсолютно позиционированный потомок
независимо от z-index. Список прячется на `hidden.bs.modal` ближайшей
модалки (защита от ESC/бэкдропа поверх открытого списка). Функция
глобальная (`window.enhanceSearchableSelect`) — вызывать вручную для
`<select>`, добавляемых в DOM динамически (см. `garages/_owner_rows_script.html`).

## Alembic + SQLite — практические заметки
- Batch-mode обязателен для ALTER на SQLite; `naming_convention` на
  `Base.metadata` даёт автоматические имена FK-констрейнтам при генерации
  (без него на FK-миграциях приходится задавать имя вручную).
- `ADD COLUMN ... NOT NULL` без дефолта падает на существующих строках —
  нужен `server_default=sa.false()`/аналог, автогенерация его не добавляет
  сама, дописывать руками в сгенерированный файл.
- `DROP COLUMN` (обычное поле) в batch-режиме простое, имени constraint'а
  не требует — в отличие от FK.
- При случайном расхождении веток (два `down_revision` от одной ревизии) —
  не создавать merge-ревизию с двумя `down_revision`, а перебазировать
  одну поверх другой (сменить `down_revision`) ради единой линейной
  истории, как и было до этого в проекте.
- Каждая миграция проверяется циклом `upgrade head → alembic check →
  downgrade → upgrade head` на БД с реальными (не пустыми) данными в
  таблице, а не только на пустой схеме.

## Прочие устоявшиеся соглашения
- `cooperative_balance()` (сумма `BankAccount.balance`, реальные деньги
  кооператива) ≠ `receivables_balance()` (сумма по лицевым счетам членов,
  сколько должны/переплатили) — не путать, только `cooperative_balance()`
  показывается как «Баланс» и на дашборде, и на `/cooperative/`.
- **Сводка балансов на странице гаража (вкладка «Информация») фильтруется
  через `can_view_member_account()` построчно** — рядовой собственник
  видит баланс только СВОЕГО `MemberAccount`, не содольщика (взносы у
  каждого свои, зависят от доли владения) — тот же принцип приватности,
  что уже применялся к лицевым счетам членов в других местах приложения,
  здесь просто ещё одно применение, не новое правило. Фильтрация — в
  роуте (Python), а не в шаблоне: список `account_summary_rows` уже
  отфильтрован до рендера, шаблон не принимает решений о видимости.
- Модалки — `modal-lg` по умолчанию (кроме случаев, где уже задан другой
  размер осознанно).
- Верификация после каждой правки: `py_compile` всех `app/*.py`,
  Jinja2-парсинг всех шаблонов, статическая сверка `url_for(...)` с
  реальными маршрутами, сверка `_()`-строк со словарём `i18n.py` (плюс
  проверка на дубли ключей через AST-обход `TRANSLATIONS`), и обязательно
  e2e через `app.test_client()` под разными ролями — статический разбор
  не ловит баги вида «затенение переменной» или «неверный дефолт роута».


## Электронное голосование — вес голоса = сумма долей по всем гаражам
Ключевое упрощение схемы: вместо бюллетеня «на гараж» — вес человека
(`voting.person_voting_weight`) = сумма его `GarageOwnership.share` по ВСЕМ
его гаражам. Из этого «1 гараж — 1 голос, делится по долям совладельцев»
получается сам собой (доли одного гаража в сумме = 1 по инварианту), а
человек с долями в нескольких гаражах голосует один раз своим суммарным
весом — не нужно спрашивать его мнение отдельно «как совладельца гаража A»
и «как совладельца гаража B». `VoteBallot` — одна запись на
(question, person), не на (question, garage, person).

**Кворум — жёсткое правило, не настраиваемое поле**: голосование
правомочно, только если приняло участие СТРОГО больше 50% от общего веса
голосов кооператива (`voting.QUORUM_THRESHOLD = Decimal("0.5")`,
`total_cooperative_weight()` = сумма долей всех гаражей). Порог принятия
решения по вопросу (`VoteQuestion.majority_threshold`, настраиваемый —
0.5 обычно, 0.6667 для квалифицированного большинства и т.п.) считается
ВСЕГДА от того же общего числа голосов кооператива, не от числа
проголосовавших по конкретному вопросу — специально убрал
альтернативную базу расчёта («от участвовавших»), которая была в первой
версии: по требованию, чтобы не было двух разных знаменателей в системе.
Из-за этого `question_results()` всегда дополнительно проверяет
`quorum_met(question.vote)` — вопрос не считается принятым, даже если
формально набрал нужную долю «за», если по голосованию в целом нет
кворума.

Статусы: `draft` (формируется повестка, черновик не виден рядовым членам)
→ `open` (приём бюллетеней, переголосование разрешено — upsert по
question_id+person_id) → `closed` (явная кнопка председателя; приём
бюллетеней прекращается и при истечении `closes_at`, даже если кнопку не
нажали — см. `is_accepting_ballots`). Протокол — не автогенерируется,
прикрепляется как обычный `Document` (как и у очных собраний) —
председатель загружает подписанный скан отдельным действием после
закрытия.

**Права**: создание/повестка/открытие/закрытие — только председатель
(`roles_required` не даёт сырой 403, а редиректит на `/dashboard` с flash
«Недостаточно прав» — так везде в проекте, не баг). Просмотр списка и
детальной страницы — все залогиненные, но черновики видны только
правлению; результаты по вопросам видны рядовым членам только после
закрытия голосования (пока идёт приём — не видны, чтобы не влиять на ещё
не проголосовавших). Голосовать может только человек с весом > 0 (владеет
долей хотя бы в одном гараже).

## Права на печать ПД-4 — разделены по видам платёжек, не по ролям целиком
Правление печатает ТОЛЬКО взносы (MemberAccount) — административный доступ
к чужим счетам ограничен этим одним видом; электричество (PersonalAccount
на гараж) правление печатать не может вообще, даже если знает garage_id
и подставит его вручную в запрос — `_print_electricity_slip()` больше не
делает исключение `is_board()`, всегда требует реального владения гаражом
(полного или частичного), независимо от роли. Рядовой член, наоборот,
может печатать/смотреть/скачивать PDF по ЛЮБЫМ своим платёжкам (оба вида)
для гаражей, которыми владеет хоть частично — `pd4._collect_member_debts()`
агрегирует взносы (+ автопеня) и электричество в одном вызове.
`_build_mixed_slips()` строит слипы вперемешку (оба вида в одном списке),
т.к. `_electricity_account_view()`-адаптер уже даёт PersonalAccount тот же
интерфейс (`.account_number/.person.full_name/.fee_type.name/.garage.number`),
что и обычный MemberAccount — шаблонам print.html/print_pdf.html не нужно
знать про разницу типов вообще, просто рендерят как есть.
**Важно**: электричество выставляется НА ГАРАЖ целиком (общий счётчик), не
разбивается по долям совладельцев — частичный собственник, печатающий
платёжку, видит и может оплатить весь остаток долга гаража, не только
свою долю (в отличие от взносов, которые физически разные MemberAccount
на разных совладельцев с самого начисления). Это не баг, так был устроен
электрический учёт с самого начала — просто теперь стал доступен ЛЮБОМУ
частичному собственнику для печати, не только полному.

Кнопка «Назад к выбору» на печатной странице раньше была завязана на флаг
`electricity` (показывалась при взносах, независимо от роли) — заменено
на `is_board()`: видна только правлению (только они выбирают печать по
нескольким людям через `/pd4/`), рядовому члену — не показывается вообще,
для любого вида платёжки.

**Побочная находка**: `pd4.select()` уже была подвержена той самой
задокументированной выше ловушке с затенением `is_board` — передавала
`is_board=is_board()` в шаблон, а `base.html` (который наследует
select.html) вызывает `is_board()` как функцию в каждой навигации →
`TypeError: 'bool' object is not callable`. Это был ПРЕДСУЩЕСТВУЮЩИЙ баг
(не внесён этой правкой), просто `/pd4/` ни разу не попадал в прошлые
smoke-тесты по ролям — вскрылся только сейчас, когда наконец написал
e2e-тест непосредственно для ПД-4. Исправлено так же, как раньше в
`garages/detail.html`: убран затеняющий kwarg, шаблон вызывает `is_board()`
напрямую. **Урок на будущее**: широкий smoke-тест «пройтись по всем
основным страницам под всеми ролями» должен реально включать ВСЕ
блюпринты, включая на первый взгляд второстепенные типа `/pd4/` — баг
пролежал необнаруженным несколько сессий именно потому, что список
проверяемых страниц в smoke-тестах не был исчерпывающим.


## API банка (`app/bank_api/`, `app/bank_sync.py`) — реализован только
## Сбербанк; auth через refresh_token + mTLS + УЦ Сбера/Минцифры + настраиваемый CP1251-формат реестров

`BankAccount.api_provider` (none/sberbank/vtb/tbank) — ВТБ/Т-Банк
выбираемы в UI («интеграция ещё не реализована»), `get_client()` для них
всегда `None`. Несколько вещей оказались упущены/неверны в первой версии
и исправлены только по мере реального тестирования кооперативом (не
предугаданы заранее) — держать в голове при следующей доработке:

0. **Авторизация — не client_credentials, а refresh_token (подтверждено
   документацией, не предположение).** Первая версия делала OAuth2
   client_credentials (только client_id+client_secret) — это в принципе
   неверный grant type для Sber API: все запросы выполняются от имени
   конкретного пользователя СберБизнес, авторизация — access_token (живёт
   60 минут, в БД не хранится) + refresh_token (живёт 180 дней, ХРАНИТСЯ
   зашифрованным в `BankApiCredential.refresh_token_encrypted`). Председатель
   получает пару access_token/refresh_token в личном кабинете Sber API
   («Ключи доступа» → сгенерировать) и вводит refresh_token в модалке
   «Настроить API» (access_token приложению вводить не нужно — оно само
   обновляет его через refresh_token перед каждым обращением к банку, см.
   `SberbankClient._get_access_token`). **Банк может при обновлении
   вернуть НОВЫЙ refresh_token взамен старого (ротация)** — старый после
   этого банк аннулирует; `SberbankClient.rotated_refresh_token`
   выставляется в этом случае, и КАЖДЫЙ роут в `bank_sync.py`,
   использующий `get_client()`, обязан вызвать
   `_persist_rotated_refresh_token(cred, client)` перед `commit()` (в т.ч.
   на пути ошибки — сам refresh мог пройти успешно, даже если последующий
   бизнес-запрос упал) — если забыть про какой-то новый роут, синхронизация
   в нём будет молча ломать refresh_token при следующей ротации.
1. **mTLS обязателен для самого TLS-соединения**, не только токен в
   заголовке. Клиентский сертификат — .pfx/.p12 из личного кабинета Sber
   API + пароль, загружается в модалке «Настроить API», конвертируется в
   PEM на сервере (`cryptography.pkcs12`), хранится в `BANK_CERTS_FOLDER`
   (НЕ `UPLOAD_FOLDER` — у того есть отдающий файлы HTTP-роут; здесь
   такого роута нет и не должно быть; права 0o700/0o600). Исходный .pfx и
   пароль нигде не сохраняются, только для разовой конвертации.
   **Личный кабинет генерирует .p12 с ЦЕПОЧКОЙ сертификатов внутри, не
   только листовым** — `_save_client_cert` сохраняет всю цепочку
   (`extra_certs` из `pkcs12.load_key_and_certificates`), не только
   `certificate`, иначе сервер банка может не принять mTLS-рукопожатие.
2. **Доверенные корни — УЦ Сбера И НУЦ Минцифры России (обе, не только
   Минцифры — подтверждено официальной документацией
   developers.sber.ru/docs/ru/sber-api/start/tls)**; обычный
   `requests`/certifi-бандл их не знает → `SSLError:
   self-signed certificate in certificate chain`. Банк отдаёт готовую
   цепочку по прямой ссылке для тестового и промышленного контуров (см.
   `Config.SBERBANK_API_CA_BUNDLE` в config.py и `.env.example` — там же
   актуальные ссылки на архивы) — надёжнее, чем собирать сертификат
   Минцифры отдельно с госуслуг, как было в первой версии.
3. **Тестовый контур подтверждён напрямую** (сообщён кооперативом из
   личного кабинета): `https://fintech-test.sberbank.ru:9443`, НЕ
   `edupirfintech.sberbank.ru`, как было угадано в первой версии.
   `SberbankClient.token_url` теперь по умолчанию выводится ИЗ base_url
   (`{base_url}/ic/sso/api/v2/oauth/token`), а не берётся отдельной
   захардкоженной константой на промышленный контур независимо от
   sandbox — это был баг первой версии (тестовый запрос всегда уходил на
   промышленный хост авторизации).
4. **Официальный перечень операций (scope) не содержит явной операции для
   реестра начислений** (developers.sber.ru/docs/ru/sber-api/start/oauth#
   polnyy-perechen-operatsiy) — `PAYMENTS_REGISTRY` («Реестр платежей»)
   там есть, а для начислений подходящей операции не нашлось вообще.
   Возможно, «приём платежей физлиц» (начисления) — отдельный, не
   входящий в Sber API продукт. Это ещё не проверено на практике (нет
   подтверждения ни в одну, ни в другую сторону) — если `send_charge_registry`/
   `get_payment_registry` будут получать отказ доступа независимо от
   корректности токенов/сертификатов, скорее всего именно поэтому; ручной
   путь (скачать/загрузить CP1251-файл через веб-интерфейс СберБизнес
   Онлайн) на этот случай уже есть и не зависит от API вообще.
5. **Реестры начислений/платежей — CP1251-текстовый файл, не JSON**, и
   формат — НАСТРАИВАЕМЫЙ (`BankRegistryFormat`, по записи на счёт), тем
   же принципом, что и CSV-импорт в мастере настройки (каталог полей +
   чекбокс/позиция в UI, см. `app/bank_api/registry_file.py:
   CHARGE_FIELD_CATALOG/PAYMENT_FIELD_CATALOG`). Значение по умолчанию —
   **реальный** формат, полученный по образцам файлов от председателя (не
   выдуманный умозрительно, как было в первой версии): реестр начислений —
   5 полей (`лицевой_счёт;ФИО;назначение;код_услуги;сумма`), точка как
   десятичный разделитель, без заголовка; реестр платежей — 13 полей,
   запятая как десятичный разделитель, плюс завершающая строка-сводка
   (`=count;total;creditedTotal;feeTotal;номерРеестра;дата`), которая
   распознаётся по настраиваемому `trailer_prefix` и пропускается при
   разборе. **Важно**: в файле реестра платежей сумма начисления
   (гасит долг члена, идёт в `Payment.amount`/FIFO) и сумма зачисления
   (реально поступило на счёт кооператива, за вычетом комиссии банка) —
   РАЗНЫЕ поля (`PaymentRegistryEntry.amount` vs `.credited_amount`/
   `.fee_amount`) — комиссия банка не должна восприниматься как недоплата
   члена. `build_registry_format()` (bank_api/__init__.py) — единственное
   место, которое строит формат из БД, используется и для автоматической
   отправки через API, и для ручного скачивания/загрузки — одна настройка
   на оба пути.

**Ручной путь всегда доступен, независимо от того, работает ли API** —
скачать/загрузить тот же CP1251-файл через веб-интерфейс СберБизнес
Онлайн (кнопки на страницах реестров), т.к. автоматическая передача через
API для этого конкретного канала (в отличие от баланса/выписки — это
современный Fintech REST/JSON) — самая неподтверждённая часть всей
интеграции: сама механика передачи именно через API, а не только вручную
через веб-интерфейс банка, тоже не проверена. Как и cbr.ru — **вся
интеграция с банком не проверялась живым запросом** (домен недоступен из
песочницы разработки), эндпоинт получения access_token тоже не
подтверждён (`SBERBANK_API_TOKEN_URL`, не зашит в код).

Реестр начислений строится из ТЕКУЩЕЙ задолженности (`balance() < 0`) по
всем лицевым счетам, не из списка `Charge` за период — известное
ограничение: нет отслеживания «этот долг уже был в реестре», повторная
отправка шлёт всю текущую задолженность заново (дублей в самом
кооперативе не создаёт — это витрина для банка, не начисление).

**Выписка тоже гасит долг автоматически, не только реестр платежей.**
Банк нередко вписывает номер лицевого счёта прямо в свободный текст
назначения платежа обычной выписки (не только в структурированном файле
реестра), например «ЛС 10640; ЧЛЕНСКИЕ ВЗНОСЫ (ФАМИЛИЯ И.О.);0126;ФАМИЛИЯ
ИМЯ» — `bank_sync.extract_account_number()` (регэксп `лс\s*[:№]?\s*(\d+)`,
регистронезависимо) распознаёт его при синхронизации выписки
(`sync_statement`), и если найденный номер совпадает с существующим
`MemberAccount`/`PersonalAccount`, **зачисление** (не списание — списания
никогда не пытаются погасить чужой долг) автоматически заводит `Payment`
на ПОЛНУЮ поступившую сумму и разносит по FIFO, без ручного подтверждения
— именно так и было явно запрошено, в отличие от реестра платежей, где
разнесение остаётся ручной кнопкой «Разнести». Общий код между реестром и
выпиской — `bank_sync._allocate_payment_to_account()`. Комиссия банка,
если она удерживается до зачисления, в выписке отдельным полем не
приходит (в отличие от файла реестра платежей, см. выше) — вся
зачисленная сумма и есть то, чем гасится долг, ничего вычитать
дополнительно не нужно.

**Если номера нет — поиск по ФИО, включая лиц для связи.** Номер лицевого
счёта в тексте есть не всегда; `_allocate_payment_to_account()` при
неудаче поиска по номеру пробует найти счёт по имени (`_resolve_account_by_name`):
- по полному ФИО плательщика (`Person.full_name`, точное совпадение без
  учёта регистра);
- по форме «Фамилия И.О.» (`_initials_key`/`_extract_initials_candidates`),
  которую банк часто указывает в самом назначении платежа для ДРУГОГО
  человека — того, за кого платят, а не плательщика (реальный пример:
  «ЧЛЕНСКИЕ ВЗНОСЫ (Ликсанов Г.Н.)» при плательщике с другой фамилией —
  типично для супруга/родственника/доверенного лица);
- среди ВСЕХ `Person`, не только собственников — совпадение с
  `GarageContact` (лицо для связи) тоже поднимает счета владельцев ЭТОГО
  гаража (`_accounts_for_person`), поскольку у самого контакта, как
  правило, своего счёта нет — предполагается, что он платит ЗА
  собственника.

Разносится ТОЛЬКО при однозначном результате. Если у найденного человека
несколько счетов (несколько видов взноса на гараж, или несколько
гаражей) — сужение идёт по совпадению `FeeType.name` с текстом назначения
платежа (`_narrow_by_fee_type`, например «ЗЕМЕЛЬНЫЙ НАЛОГ» текстом сузит
до счёта именно этого вида взноса); если и после сужения кандидатов
больше одного (или совпадений по имени вообще нет) — платёж остаётся
неразнесённым, риск отнести чужой платёж не туда важнее автоматизации.
Тот же путь используется и в ручном «Разнести» (для выписки и для
реестра платежей) — председатель может явно переопределить номер счёта в
форме, если автоматика ошиблась или не справилась.


# Хронология сессий (сжато)

1. **Объединение вкладок «Электричество» и «Счёт»** гаража в одну, с реальной
   связью показание↔начисление через FK `Charge.reading_id` (была только
   текстом в комментарии). Отдельная страница «Начисления на гаражи»
   позже слита с массовым начислением (см. п.8).
2. **ПД-4 для электросчёта гаража** — печать долга по общему счётчику
   гаража, не только по счетам членов; QR через `pd4_qr_payload_electricity()`.
3. **FIFO-разнесение платежей введено впервые** (для гаражей/электричества) —
   `ChargeAllocation`, статусы «оплачено/частично/не оплачено» в журнале.
   Позже (см. принципы выше) обобщено и на счета членов ради пени.
4. **Один платёж — одна строка** в журнале начислений (использует уже
   существующую связь `ChargeAllocation`, раньше строки сопоставлялись
   чисто позиционно через `zip_longest`, без реальной связи в данных).
5. **Валидация показаний счётчика** — запрет ввода меньше предыдущего;
   правка последнего показания доступна только председателю (не переписываем
   историю задним числом никому другому).
6. **Аудит доступа** — найдены и закрыты реальные дыры (чужие `/persons/<id>`,
   `/garages/<id>`, фото гаража, ПД-4 по чужим счетам были доступны без
   проверки владения). Плюс: смена своего пароля, поиск в длинных select'ах
   (стало `enhanceSearchableSelect`), чек-лист гаражей для массового начисления.
7. **Баланс кооператива = сумма расчётных счетов**, не сумма ожидаемых
   поступлений от членов (появилось разделение `cooperative_balance()` /
   `receivables_balance()`, см. принципы). Плюс модуль расчётов с
   контрагентами (начальный баланс, правка последнего платежа, сторно).
8. **Права доступа централизованы** в `permissions.py` (было продублировано
   по разным модулям под разными именами). Единый стиль кнопок по проекту.
   Убран дубль страниц начисления — `/garages/charges/add` слита в
   `/finance/mass-charge` (чекбоксы выбора гаражей перенесены туда же).
9. **Расчётные счета/баланс/комментарий кооператива скрыты** от рядовых
   членов на `/cooperative/` (были видны всем залогиненным).
10. **Созывы правления + ревизионная комиссия** — `BoardTerm`/`BoardMember`
    (были в схеме, не использовались) заработали по-настоящему, привязаны
    к протоколу общего собрания. Применение состава — отдельная явная
    кнопка (см. принципы, риск самоблокировки).
11. Старые чекбоксы флагов правления на карточке человека убраны (созывы —
    единственный путь); `Cooperative.balance` как ручное поле удалено из
    схемы, «Баланс» стал вычисляемым.
12. **Бухгалтер отделён от созыва правления** — назначается председателем
    напрямую, не общим собранием, не обязан быть членом правления
    (см. принципы). Явная роль «член правления» в таблице состава.
13. **Автоматическое начисление пени** — новый модуль `penalty.py`, интеграция
    с ключевой ставкой ЦБ РФ, обобщение FIFO на счета членов (см. принципы,
    несколько подпунктов выше — это самая насыщенная сессия по граблям).
14. **Слияние параллельных веток** (пеня + рефакторинг бухгалтера,
    разошедшихся от одной ревизии) — файл за файлом вручную, миграция
    пени перебазирована поверх миграции бухгалтера ради линейной истории.

    (был реальный баг — владелец пропадал целиком, а не просто получал
    доли по умолчанию).
16. **Электронное голосование** (очно-заочное/заочное) + крон-скрипт

28. **Живая проверка API Сбербанка — исправление реальных ошибок после
    первого подключения кооперативом (не предугадано заранее).** Три
    независимые находки, все подтверждены официальной документацией или
    напрямую личным кабинетом кооператива — подробности см. в разделе
    принципов выше («API банка»):
    - авторизация была client_credentials, а должна быть
      access_token/refresh_token — `BankApiCredential.refresh_token_encrypted`
      (новое поле), `SberbankClient` переписан на `grant_type=refresh_token`
      с обработкой ротации токена (`rotated_refresh_token` +
      `bank_sync._persist_rotated_refresh_token`, вызывается в каждом
      роуте, использующем `get_client()`);
    - тестовый хост был угадан неверно (`edupirfintech.sberbank.ru`) —
      исправлен на подтверждённый `fintech-test.sberbank.ru:9443`,
      заодно исправлен баг: `token_url` раньше был захардкожен на
      промышленный хост независимо от sandbox, теперь выводится из
      `base_url`;
    - CA-бандл — не только Минцифры, а Сбер+Минцифры вместе, с прямыми
      ссылками на готовые архивы от банка вместо сборки вручную с
      госуслуг (`config.py`/`.env.example`);
    - `_save_client_cert` (`app/bank_sync.py`) теперь сохраняет всю
      цепочку сертификатов из `.p12`, а не только лист — личный кабинет
      Sber API кладёт цепочку внутрь контейнера.
    Также задокументирована (но не проверена и не исправлена — нечего
    исправлять без доступа к реальному Swagger) находка: официальный
    перечень scope-операций не содержит явной операции для реестра
    начислений — возможно, это отдельный от Sber API продукt.
29. **Скрипт восстановления БД (`scripts/restore_db.py` + обёртка
    `restore_db.sh`)** — симметричен `backup_db.py`/`backup_db.sh` по
    конвенциям (`DATABASE_PATH`/`BACKUP_DIR` из окружения, тот же venv-
    автоопределение в `.sh`). `--list` выводит бэкапы `coop_*.db` с
    размером/датой; `--restore N|ИМЯ|latest` восстанавливает через тот
    же `sqlite3.backup()` API, которым и создаётся бэкап (не `cp`).
    Перед перезаписью текущая БД сама сохраняется в `BACKUP_DIR` как
    `pre_restore_<timestamp>.db` — восстановление, соответственно, тоже
    откатываемо этим же скриптом. И у бэкапа-источника, и у результата
    восстановления проверяется `PRAGMA integrity_check`; запись идёт во
    временный файл `<DB_PATH>.restoring` с последующим атомарным
    `os.replace()`, чтобы сбой посреди записи не испортил рабочую БД;
    после подмены удаляются устаревшие `-wal`/`-shm` (иначе при
    следующем открытии БД WAL от предыдущего состояния мог бы
    перекрыть восстановленные данные). Интерактивное подтверждение по
    умолчанию, `--yes` для сценариев без TTY. Не предназначен для
    cron — README прямо говорит, что это ручная операция.

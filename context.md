# Архитектурные принципы и грабли

## FIFO-разнесение платежей (ChargeAllocation)
Единый механизм для гаражей (электричество) и счетов членов (взносы/пеня):
`accounting._reallocate_fifo(charges, payments)`, обёртки
`reallocate_garage_charges(garage)` / `reallocate_member_charges(account)`.
Вызывать явно после ЛЮБОГО добавления `Charge`/`Payment` — не автоматически.
Идемпотентна (пересчёт с нуля), безопасна для повторного вызова.
`balance()` (агрегатная сумма) от `ChargeAllocation` не зависит — отдельный
путь для точного остатка по датам (пеня, статусы в журнале начислений).

## CSV-импорт в мастере настройки — настраиваемый формат
`CsvImportProfile` (по записи на тип: people/garages) хранит `columns` —
JSON-список ключей в порядке файла председателя, переиспользуется. UI —
попап: чекбокс (есть/нет) + числовое поле позиции (не drag-and-drop —
проще, без JS-библиотек, работает без риска потери состояния). Обязательные
колонки — чекбокс `disabled` + скрытое поле с тем же именем (браузер не
шлёт значение задизейбленного чекбокса). Парсинг — `dict(zip(columns, cells))`,
код обращается по `values.get("full_name")`, не по позиции. Образец CSV
(`_build_template_csv`) строится из того же активного формата.
`_looks_like_header_row()` — совпадение ЛЮБОЙ ячейки первой строки (без
регистра) с подписью любой колонки каталога (не только первой ячейки).
Формат: запятая-разделитель, UTF-8 (`utf-8-sig` для BOM), числа только с
точкой (не путать с разделителем при экспорте из Excel RU-локали).
Гаражи: несколько строк с одним номером = несколько собственников;
отсутствующий человек создаётся по ФИО (`_find_or_create_person_by_name`,
без регистра). Импорт идемпотентен: существующие гаражи/связи не
дублируются, только обновляют долю.

## Мастер первоначальной настройки (`/setup`, только председатель)
Оркестрация, не дублирование: там, где уже есть полноценная страница
(`garages.create`, `governance.term_detail`) — только точка входа, не
свои формы. Свои формы — только для того, чего не было вообще (CSV-импорт;
короткие формы кооператив/счёт/тариф/поставщик/счётчик). Статус шага —
вычисляется по данным (`wizard_status()`), не персистентный флаг — можно
открывать в любом порядке без риска рассинхронизации. Первый созыв
правления — `board_init()` создаёт `BoardTerm` с `elected_by_meeting_id=None`
напрямую (в обычном режиме `create_term()` требует протокол — на старте
избирать было не из чего, это не баг). Грабли: председатель из `seed.py` —
`person_id=None`, `sync_user_role()` не находит `User` при обычном
применении состава → `board_link_me()` — быстрая привязка на шаге правления.

## Новости — markdown + вложения (`news_format.py`, `News`, `NewsAttachment`)
Упрощённый markdown (`Markdown` + `nl2br`) → `bleach.clean()` (без `img`/
`script` — картинки идут отдельно через `NewsAttachment`) → `bleach.linkify()`.
Превью (`excerpt()`) — отдельный проход через `plain_text()` (markdown→HTML→
strip), не обрезка готового HTML (риск порвать тег). `news_format.py` не
завязан на модель News — переиспользован для вики (см. хронологию, сессия 34).

## Alembic — общие практические заметки (SQLite)
- Batch-mode обязателен для ALTER; `naming_convention` на `Base.metadata`
  даёт автоимена FK при автогенерации.
- `ADD COLUMN NOT NULL` без дефолта падает на существующих строках —
  дописывать `server_default=sa.false()`/аналог руками, автогенерация не
  добавляет сама.
- `DROP COLUMN` в batch — просто, имени constraint'а не требует (в отличие
  от FK).
- Расхождение веток (два `down_revision`) — не merge-ревизия, а
  перебазировка одной поверх другой (линейная история).
- Каждая миграция: `upgrade head → alembic check → downgrade base →
  upgrade head`, по возможности на БД с реальными (не пустыми) данными.
- История миграций один раз сбрасывалась до baseline-ревизии (по прямой
  просьбе, пока проект не был на боевых данных) — больше так делать нельзя.
- Частичный уникальный индекс («уникально только среди активных записей»,
  чтобы архивная запись и её преемник могли законно делить один и тот же
  «человекочитаемый» идентификатор — номер счёта, код и т.п.): обычный
  `UniqueConstraint`/`unique=True` на колонке для этого не годится (видит
  все строки). Вместо него — `Index(..., unique=True, sqlite_where=text(...),
  postgresql_where=text(...))` в `__table_args__` модели; в миграции —
  `op.create_index(..., unique=True, sqlite_where=...)` ОТДЕЛЬНО от
  `batch_alter_table` (создание индекса в SQLite не требует батч-режима,
  батч нужен только чтобы ДРОПНУТЬ старый обычный constraint). См.
  `MemberAccount.is_archived`/`account_number` — раздел 39 хронологии.

## Автоначисление пени (`penalty.py`)
Формула: непогашенный остаток × ключевая ставка ЦБ × 1/300 (первые 30 дней)
/ 1/150 (с 31-го) × дни, посуточно, по реальным датам платежей (через
`ChargeAllocation`). Считается на лету при открытии `/dashboard` и
`/finance/penalty/` (`accrue_penalties(today)`, без flash);
`Charge.penalty_calculated_through` делает повторный вызов почти no-op.
Персистентные `Charge`-записи нужны (не виртуальное число) — иначе нечем
платить и нечего печатать в ПД-4. Кнопка «Пересчитать на дату» — для
прошлой даты (отчёты), не обязательный шаг. **Известное ограничение**:
задним числом внесённый платёж ПОСЛЕ расчёта пени за эти дни не
пересчитывает её ретроактивно, только продолжает считать вперёд.

## cbr.ru (ключевая ставка) — daily-дамп, не список изменений
SOAP `DailyInfoWebServ/DailyInfo.asmx`, метод `KeyRate` — запись на КАЖДЫЙ
день. Сжимается в `penalty._compress_to_change_points()` (на входе) и
`compact_key_rates()` (по сохранённой истории). `is_manual=True` не
сжимается/не удаляется. Ответ — diffgram (настоящие XML-элементы, не
экранированная строка) — парсер ищет `DT`+`Rate` по всему дереву без
привязки к namespace. **Живой ответ cbr.ru ни разу не тестировался**
(домен недоступен из песочницы) — первое место для проверки при сбое.

## Права доступа — только через permissions.py
`is_board()`/`is_chairman()`/`is_privileged()`/`is_owner_or_board()`/
`can_view_member_account()` — единственное место проверки ролей. Первые три
пробрасываются в Jinja через `_inject_user()`. **Грабли с затенением**: не
кэшировать `is_board()` в переменную с тем же именем
(`{% set is_board = is_board() %}`) — `{% include %}` передаёт контекст
целиком, внутри инклюда вызов ожидает функцию, получает bool →
`TypeError: 'bool' object is not callable`. Ловится только реальным
рендером (не статическим Jinja-парсингом) — этот баг находили дважды
независимо (`garages/detail.html`, `pd4/select.html`) и на будущее нужен
e2e-рендер под ролями по ВСЕМ блюпринтам, включая второстепенные.
`roles_required`/`ROLE_LEVEL` (auth.py) — доступ к роуту целиком (декоратор,
минимальная роль); `permissions.py` — доступ к объекту внутри роута (свой
это гараж/счёт или нет). Разные уровни, не путать.

## Правление и созывы
`governance.apply_term()` — явная кнопка, НЕ авто при добавлении членов
(иначе председатель, заполняющий состав, рискует потерять флаг у себя
самого на середине). Бухгалтер — НЕ через созыв: назначается председателем
напрямую (`/governance/accountant/set|unset`), может не быть членом
правления, применяется сразу (риска самоблокировки нет).

## Searchable select — рендерится в <body>, не внутри формы
`base.html: enhanceSearchableSelect()` — общий JS для `<select data-searchable>`.
Список — прямой потомок `document.body`, `position: fixed` (координаты от
`getBoundingClientRect()`, пересчёт на scroll/resize) — не внутри
`position-relative`-обёртки, т.к. `modal-dialog-scrollable` ставит
`overflow-y:auto` на `.modal-body`, что обрезает абсолютно позиционированных
потомков независимо от z-index. Прячется на `hidden.bs.modal`. Глобальная
(`window.enhanceSearchableSelect`) — вызывать вручную для динамически
добавляемых `<select>`.

## Прочие устоявшиеся соглашения
- `cooperative_balance()` (сумма `BankAccount.balance`, реальные деньги) ≠
  `receivables_balance()` (сумма лицевых счетов членов, кто сколько должен)
  — не путать; на дашборде и `/cooperative/` показывается только первое.
- Приватность лицевых счетов — `can_view_member_account()` фильтрует
  построчно (сводка на странице гаража, счета членов) в РОУТЕ (Python), не
  в шаблоне — рядовой собственник видит только свой счёт, не содольщика.
- Модалки — `modal-lg` по умолчанию.
- Верификация после каждой правки: `py_compile`, Jinja2-парсинг всех
  шаблонов, статическая сверка `url_for` с маршрутами, сверка `_()`-строк
  с `i18n.py` (+AST-проверка дублей ключей), и e2e через
  `app.test_client()` под разными ролями — статический разбор не ловит
  затенение переменных или неверные дефолты роутов.

## Электронное голосование (`voting.py`)
Вес голоса = сумма долей по ВСЕМ гаражам человека
(`voting.person_voting_weight`), не «бюллетень на гараж» — `VoteBallot`
одна запись на (question, person). Кворум — жёсткое правило (не
настраиваемое поле): >50% от общего веса кооператива
(`QUORUM_THRESHOLD=Decimal("0.5")`, `total_cooperative_weight()`). Порог
принятия по вопросу (`VoteQuestion.majority_threshold`, настраиваемый)
считается ВСЕГДА от общего числа голосов кооператива, не от
проголосовавших по вопросу — специально убран альтернативный знаменатель.
`question_results()` дополнительно проверяет `quorum_met()`. Статусы:
draft (не виден рядовым) → open (upsert по question_id+person_id,
переголосование разрешено) → closed (явная кнопка председателя; приём
прекращается и при истечении `closes_at`, даже без кнопки). Протокол —
обычный `Document`, не автогенерируется. Права: создание/повестка/
открытие/закрытие — только председатель; черновики видны только правлению;
результаты по вопросам — рядовым только после закрытия. Голосовать может
только человек с весом > 0.

**VoteType.IN_PERSON** (третий вид, наряду с absentee/in_person_and_absentee)
— решение уже принято на собрании, электронная повестка не заводится:
`Vote` создаётся сразу в CLOSED (`opens_at == closes_at` = дата собрания),
`Document` с протоколом создаётся и привязывается атомарно. Автогенерация
Alembic на это дала пустую миграцию (длина VARCHAR не меняется, SQLite не
enforce-ит enum) — удалена как бесполезная.
**`set_ballot_for_person()`** — председатель вручную записывает бюллетень
за члена (только RoleEnum.CHAIRMAN); работает только для
IN_PERSON_AND_ABSENTEE и только пока OPEN; переиспользует `cast_ballots()`
— последующее самостоятельное голосование участника корректно перезаписывает
запись председателя (UniqueConstraint(question_id, person_id), последняя
подача побеждает). В отличие от бюллетеня участника, для председателя
разрешена частичная запись. `eligible_voters()` — люди с весом > 0,
отсортированы по ФИО.

## Права на печать ПД-4 — разделены по видам платёжек, не по ролям целиком
Правление печатает ТОЛЬКО взносы (MemberAccount) — электричество
(PersonalAccount) правление не печатает вообще, даже подставив garage_id
вручную (`_print_electricity_slip()` требует реального владения, без
исключения для is_board()). Рядовой член печатает ЛЮБЫЕ свои платёжки
(взносы+электричество) по гаражам, которыми владеет хоть частично.
`_electricity_account_view()`-адаптер даёт PersonalAccount интерфейс
MemberAccount — шаблоны печати не знают о разнице типов.
**Важно**: электричество выставляется на гараж целиком (общий счётчик) —
частичный собственник видит и может оплатить весь остаток, не только
свою долю (не баг, так было всегда, просто доступно теперь любому
частичному собственнику). Кнопка «Назад к выбору» — видна только
`is_board()` (было завязано на флаг вида платёжки, что не соответствовало
роли).

## API банка (`app/bank_api/`, `app/bank_sync.py`) — реализован только Сбербанк
`BankAccount.api_provider` (none/sberbank/vtb/tbank) — ВТБ/Т-Банк
выбираемы в UI, но `get_client()` для них всегда `None`.

0. **Авторизация — refresh_token, не client_credentials** (подтверждено
   документацией). Все запросы — от имени конкретного пользователя
   СберБизнес: access_token (60 мин, не хранится) + refresh_token (180
   дней, зашифрован в `BankApiCredential.refresh_token_encrypted`).
   Председатель вводит refresh_token в модалке «Настроить API» (access_token
   не нужен — обновляется сам, см. `SberbankClient._get_access_token`).
   **Ротация**: банк может вернуть новый refresh_token, старый
   аннулируется — `SberbankClient.rotated_refresh_token`; КАЖДЫЙ роут в
   `bank_sync.py`, вызывающий `get_client()`, обязан вызвать
   `_persist_rotated_refresh_token(cred, client)` перед `commit()`,
   включая путь ошибки (refresh мог пройти даже если бизнес-запрос упал).
1. **mTLS обязателен для TLS-соединения**, не только токен в заголовке.
   .pfx/.p12 из ЛК Sber API + пароль → PEM (`cryptography.pkcs12`),
   хранится в `BANK_CERTS_FOLDER` (НЕ `UPLOAD_FOLDER` — нет отдающего
   роута), права 0o700/0o600. Исходный .pfx/пароль не сохраняются.
   **.p12 содержит ЦЕПОЧКУ сертификатов** — `_save_client_cert` сохраняет
   всю (`extra_certs`), не только лист, иначе mTLS-рукопожатие может не
   пройти.
2. **Доверенные корни — УЦ Сбера И НУЦ Минцифры** (обе, подтверждено
   developers.sber.ru/docs/ru/sber-api/start/tls) — обычный certifi-бандл
   не знает → `SSLError: self-signed certificate in certificate chain`.
   Банк отдаёт готовую цепочку по прямой ссылке (см. `Config.SBERBANK_API_CA_BUNDLE`,
   `.env.example`).
3. **Тестовый контур**: `https://fintech-test.sberbank.ru:9443` (подтверждено
   ЛК кооператива), НЕ `edupirfintech.sberbank.ru` (был баг первой версии).
   `token_url` теперь выводится ИЗ `base_url`
   (`{base_url}/ic/sso/api/v2/oauth/token`), не захардкожен на промышленный
   хост.
4. **Официальный перечень scope-операций не содержит реестра начислений**
   (`PAYMENTS_REGISTRY` есть, для начислений — нет) — возможно, отдельный
   продукт, не проверено ни в одну сторону. Ручной путь (CP1251-файл через
   веб-интерфейс СберБизнес Онлайн) не зависит от API.
5. **Реестры — CP1251-текст, настраиваемый формат** (`BankRegistryFormat`,
   тот же принцип, что CSV-импорт — каталог полей + чекбокс/позиция, см.
   `bank_api/registry_file.py: CHARGE_FIELD_CATALOG/PAYMENT_FIELD_CATALOG`).
   Дефолт — **реальный** формат по образцам от председателя: реестр
   начислений — 5 полей (`лицевой_счёт;ФИО;назначение;код_услуги;сумма`),
   точка как разделитель, без заголовка; реестр платежей — 13 полей,
   запятая как разделитель, плюс строка-сводка (`trailer_prefix`,
   распознаётся и пропускается). **Сумма начисления vs сумма зачисления —
   разные поля** (`PaymentRegistryEntry.amount` vs `.credited_amount`/
   `.fee_amount`) — комиссия банка не должна восприниматься как недоплата.
   `build_registry_format()` — единственное место сборки формата из БД,
   для API и для ручного скачивания/загрузки одинаково.

Ручной путь (скачать/загрузить CP1251-файл через веб-интерфейс банка)
всегда доступен независимо от API — сама механика передачи реестров
именно через API не подтверждена. **Вся интеграция с банком и cbr.ru не
проверялась живым запросом** из песочницы разработки; эндпоинт
access_token тоже не подтверждён (`SBERBANK_API_TOKEN_URL`).

Реестр начислений строится из ТЕКУЩЕЙ задолженности (`balance() < 0`), не
из списка `Charge` за период — известное ограничение: нет отслеживания
«уже в реестре», повторная отправка шлёт всё заново (дублей в кооперативе
не создаёт — это витрина для банка).

**Выписка тоже гасит долг автоматически.** Банк нередко вписывает номер
лицевого счёта в свободный текст назначения обычной выписки, например
«ЛС 10640; ЧЛЕНСКИЕ ВЗНОСЫ...» — `bank_sync.extract_account_number()`
(regex `лс\s*[:№]?\s*(\d+)`, без регистра) распознаёт при `sync_statement`;
при совпадении с существующим счётом **зачисление** (не списание)
автоматически заводит `Payment` на полную сумму и разносит по FIFO без
подтверждения — так и запрошено (в отличие от реестра платежей, где
разнесение — ручная кнопка «Разнести»). Общий код —
`bank_sync._allocate_payment_to_account()`. Комиссия банка в выписке
отдельным полем не приходит — вся зачисленная сумма гасит долг как есть.

**Если номера нет — поиск по ФИО, включая лиц для связи.**
`_resolve_account_by_name()`: полное ФИО плательщика → форма «Фамилия И.О.»
(банк часто указывает того, ЗА КОГО платят, не плательщика) → среди ВСЕХ
`Person`, включая `GarageContact` (лицо для связи поднимает счета
владельцев гаража — у контакта обычно нет своего счёта). Разносится
ТОЛЬКО при однозначном результате; при нескольких кандидатах — сужение по
`FeeType.name` в тексте назначения (`_narrow_by_fee_type`); если и после
этого не однозначно — остаётся неразнесённым (риск отнести чужой платёж
важнее автоматизации). Тот же путь и в ручном «Разнести».

## Вики (`app/wiki.py`, `WikiPage`) — справочные заметки, не хронологическая лента
В отличие от News (лента событий/объявлений) — набор страниц-справок
(параметры видеонаблюдения, схема сети, телефоны контрагентов и аварийных
служб), правятся по мере необходимости, организованных ДЕРЕВОМ разделов/
подразделов (`WikiPage.parent_id`, самоссылающийся FK, глубина не
ограничена — раздел это обычная страница, просто с детьми, у него тоже
может быть свой текст). Формат тела — тот же markdown, что у новостей:
`news_format.py` переиспользован как есть, зарегистрирован вторым
jinja-глобалом `render_wiki_html` (та же функция `render_html`, отдельное
имя для ясности в шаблонах). Создают/редактируют/удаляют только правление
(как документы). Видимость для ЧТЕНИЯ — `WikiPage.is_internal`,
настраивается ПО СТРАНИЦЕ (выбор из 3 обсуждавшихся вариантов: все члены /
только правление / по странице — тот же принцип, что у `Document.is_internal`:
дерево скрывает внутренние страницы для не-правления, прямой переход по id
даёт 403, не просто отсутствие ссылки). Пункт «Вики» — в основной
навигации (не в дропдауне правления, как «Новости») — дерево видно любому
вошедшему, просто отфильтровано.

**Дерево навигации** — `wiki._build_visible_tree()`: строит вложенную
структуру из ПОЛНОГО списка страниц с учётом видимости зрителя. Ключевой
нюанс: если скрытым (is_internal) сделан ЦЕЛЫЙ раздел, а какой-то из его
подразделов остался общедоступным — этот подраздел не пропадает у
рядового члена, а поднимается к ближайшему видимому предку (или в
корень) — иначе видимая страница стала бы недостижимой только из-за
того, что раздел над ней сделали внутренним («дыра» в дереве). Рендер —
`wiki/_tree.html`, рекурсивный Jinja-макрос + Bootstrap `collapse`
(никакого дополнительного JS): ветка с текущей просматриваемой страницей
раскрыта по умолчанию (через `path_ids`, предки + сама страница), прочие
ветки свёрнуты. Сортировка внутри уровня — по алфавиту, без отдельного
поля для ручного порядка (можно добавить позже, структуру дерева это не
меняет).

**Удаление раздела с непустыми детьми запрещено** — и explicit-проверкой
в `wiki.delete()` (понятное сообщение, до похода в БД), и
`ondelete="RESTRICT"` на FK как страховка (SQLite FK enforcement включён
глобально, см. `database.py: PRAGMA foreign_keys=ON`). При выборе
родителя в форме (`_parent_options()`) нельзя выбрать саму страницу или
её потомка — проверяется на СЕРВЕРЕ (`_descendant_ids()`), не только
исключением из `<select>`, иначе можно было бы обойти через прямой POST.

Раньше вместо дерева была плоская `category` (свободный текст) — заменена
при переходе на иерархическую навигацию. Миграция `e80abefa5b98`
бэкофиллит без потери данных: для каждого использованного значения
`category` создаётся НОВАЯ корневая страница-раздел с этим названием
(`is_internal=False` по умолчанию), все страницы этой категории становятся
её детьми — проверено на реальных тестовых данных перед прогоном полного
цикла (`upgrade → alembic check → downgrade base → upgrade head`).
`downgrade()` восстанавливает колонку `category`, но НЕ содержимое —
данные необратимо переходят в структуру дерева (осознанное ограничение,
обычное дело для downgrade реальных данных).

## Inline-картинки в теле новости/вики (`NewsAttachment`/`WikiAttachment`)
Кнопка «Вставить картинку» в тулбаре форм — выбор из 2 подходов
(двухшаговое сохранение с последующей вставкой vs AJAX-загрузка на лету):
выбран AJAX — файл грузится СРАЗУ по выбору (POST
`/news|wiki/attachments/upload`, board-only, белый список расширений
jpg/png/webp/gif через `garages.ALLOWED_PHOTO_EXT`), ссылка `![](url)`
вставляется в textarea в позицию курсора без ожидания сохранения самой
статьи. `news_format.py`: тег `<img src alt>` разрешён в bleach whitelist
(картинка markdown — часть core-синтаксиса, доп. расширений не нужно).

**Проблема курицы и яйца** — картинка получает `id`/URL раньше, чем
существует сама статья (которая ещё пишется). Решение: `news_id`/
`page_id` NULLABLE — при AJAX-загрузке создаётся «осиротевшее» вложение
(`is_inline=True` у News; у Wiki отдельного `is_inline` не нужно — там
ВСЕ вложения по смыслу inline, нет отдельной галереи). При сохранении
статьи (`create()`/`edit()`) `_sync_inline_attachments(item, body_text)`:
регуляркой находит id вложений, упомянутых в НОВОМ тексте, «забирает» из
них те, что осиротевшие И принадлежат текущему автору (`author_id` —
чужое осиротевшее вложение по одной ссылке в тексте не подхватывается,
проверено тестом `test_cannot_claim_another_authors_orphan` — иначе можно
было бы «угнать» чужую загрузку); прикреплённые ранее inline-вложения,
ссылку на которые из текста убрали при правке — удаляются автоматически
(вместе с файлом на диске). У News классические галерейные вложения
(`is_inline=False`, блок «Добавить фото или файлы») этой синхронизацией не
затрагиваются — управляются только чекбоксами `remove_attachment`,
отдельная логика; в шаблонах галерея под текстом фильтрует
`rejectattr("is_inline")`, чтобы вставленные в текст картинки не
дублировались снизу.

**Удаление файла с диска — общий SQLAlchemy `after_delete`-listener**
(`app/models.py: _delete_attachment_file`, один обработчик и на
`NewsAttachment`, и на `WikiAttachment`) — раньше при удалении строки
файл на диске оставался висеть при ЛЮБОМ пути удаления (чекбокс, каскад
при удалении статьи/страницы, cron-очистка); теперь один хук покрывает
все пути. `current_app`/`os` импортируются лениво внутри обработчика
(избегаем завязки models.py на Flask-контекст на уровне модуля).

**Видимость файла вики наследует видимость страницы** — `wiki.attachment()`
даёт 403 не-правлению, если `att.page.is_internal`; для ЕЩЁ не сохранённого
(осиротевшего, `page is None`) вложения по умолчанию считаем его
внутренним — не должны отдавать «неизвестно что» анонимно/рядовому члену
до того, как определилась итоговая видимость страницы. У News вложения
остаются полностью публичными (как и вся лента) — без изменений в модели
доступа, осиротевшие в том числе (согласовано с уже существующим
поведением ленты, не новый риск).

**Осиротевшие вложения чистит `scripts/cleanup_orphan_attachments.py` по
cron** (обёртка `.sh` — тот же паттерн, что `update_key_rate.sh`: venv,
`flock`, лог) — удаляет (через ORM `db_session.delete`, чтобы сработал
`after_delete`-listener и файл тоже удалился) вложения без родителя
старше 24 часов. Порог намеренно не мгновенный — правление может писать
статью с перерывами, вкладка может быть открыта день.

[← К оглавлению](../README.md)

Установка зависимостей и первый запуск для разработки — в
[README](../README.md#быстрый-старт), установка на сервер по шагам (с

## Переменные окружения

Полный список — в `.env.example`. Обязательно задать перед реальным
деплоем:

- `SECRET_KEY` — без него приложение стартует (для удобства локальной
  разработки), но с небезопасным дефолтным ключом и явным предупреждением
  в логе. Сгенерировать: `python3 -c "import secrets; print(secrets.token_hex(32))"`.
- `DATABASE_URL` — если БД не лежит в дефолтном `instance/coop.db`.
- `INSTANCE_DIR` — каталог данных экземпляра сайта (БД `coop.db`,
  `uploads/`, `dvr/`, `bank_certs/`, `backups/`, логи и блокировки
  cron-скриптов), по умолчанию `instance/` в корне проекта. Нужен, чтобы
  запускать несколько кооперативов с одного checkout'а кода — см.
  [ниже](#несколько-кооперативов-на-одном-сервере).
- `FORCE_HTTPS=1` — включает `Secure`-флаг на cookie сессии; ставить,
  только если приложение реально работает по HTTPS (за реверс-прокси).
- `BEHIND_PROXY=1` — приложение за реверс-прокси (nginx): доверять его
  заголовкам `X-Forwarded-For/-Proto/-Host` (werkzeug `ProxyFix`). Без
  этого за nginx все посетители для приложения — `127.0.0.1`: лимит
  попыток входа общий на всех (один перебирающий пароли блокирует вход
  остальным), reCAPTCHA получает не тот адрес, ссылки в уведомлениях —
  `http://`. Без прокси не включать — заголовки подделал бы любой.

## Деплой в проде

Фласковский `python run.py` (со встроенным dev-сервером) годится только
для локальной разработки — он однопоточный и не рассчитан на реальную
нагрузку. Для реального деплоя:

```bash
pip install gunicorn
gunicorn -w 2 -b 127.0.0.1:8000 run:app
```

`-w 2` (2 воркера) — с оговоркой: **rate limiting на `/auth/login`
(Flask-Limiter) по умолчанию хранит счётчики в памяти процесса
(`memory://`)**, то есть не разделяется между воркерами — с несколькими
воркерами лимит фактически умножается на их число. Для одного воркера
(`-w 1`) это не проблема; для нескольких — задайте `RATELIMIT_STORAGE_URI`
(например, `redis://localhost:6379`) и поставьте `redis`-сервер, тогда
лимиты будут общими для всех воркеров.

На маленьком сервере (1 ГБ ОЗУ) вместо нескольких процессов лучше один
процесс с потоками:

```bash
gunicorn -w 1 --threads 4 -k gthread -b 127.0.0.1:8000 run:app
```

Каждый процесс приложения занимает ~120 МБ, а нагрузка у кооператива —
единицы одновременных запросов, в основном ожидание БД/сети, с которым
потоки справляются не хуже процессов. Заодно лимиты Flask-Limiter снова
общие (один процесс — одна память), без redis. Сессии БД — по потоку
(`scoped_session`), SQLite в режиме WAL.

Перед gunicorn — nginx (или другой реверс-прокси) с HTTPS (Let's Encrypt/
certbot) и статикой, gunicorn держите на `127.0.0.1`, наружу не открывайте.
Пример systemd-юнита и конфига nginx (статика мимо приложения, кэш на год
для `app/static/vendor/`, заголовки прокси, лимит размера загрузки,
таймаут, gzip) — в [INSTALL.md](../INSTALL.md); это пример для
Debian/Ubuntu, на другой ОС пути и команды будут свои.

Сервер с нуля, с переносом БД и файлов `instance/` — Ansible-плейбук
[`deployment/ansible`](../deployment/ansible/README.md). Обновления —
[`deployment/deploy.sh`](../deployment/deploy.sh)
с заглушкой «Ведутся технические работы» на время обновления
(`deployment/deploy/maintenance.html`, nginx отдаёт её с кодом 503 по флагу
`deployment/deploy/maintenance.on`, а также при 502/504 — пока gunicorn
перезапускается; фрагмент конфига — `deployment/deploy/nginx-maintenance.conf`),
см. [INSTALL.md](../INSTALL.md#обновление).

Чек-лист перед первым реальным запуском:
1. `SECRET_KEY` задан переменной окружения (не дефолтный).
2. `FLASK_DEBUG` не установлен (или `=0`) — иначе интерактивный
   Werkzeug-дебаггер даёт произвольное выполнение кода через браузер.
3. `FORCE_HTTPS=1`, если есть HTTPS; `BEHIND_PROXY=1`, если перед
   приложением nginx.
4. Cron для `update_key_rate.sh` и `backup_db.sh` настроен.
5. Пароль `chairman` сменён с дефолтного `change-me-please`.
6. `pip install gunicorn` (или другой WSGI-сервер) — не `python run.py`.

### Журнал внешних API

Все HTTP-запросы приложения и cron-скриптов к внешним сервисам (СберБизнес,
eWeLink, СМС Аэро, Telegram, Beget, ТНС-Энерго…) пишутся в
`instance/logs/external_api-ГГГГ-ММ-ДД.log`:
адрес, тело запроса, статус, время и тело ответа или исключение (TLS,
таймаут). Токены, пароли и ключи маскируются, заголовок `Authorization` не
пишется. Хранится `API_LOG_KEEP_DAYS` дней (7; при опросе eWeLink и Telegram раз в минуту — порядка 15 МБ в сутки; файлы за позавчера и раньше сжимаются gzip в `*.log.gz`), тела обрезаются до
`API_LOG_MAX_BODY` символов (200 000 — чтобы страница выписки банка попадала целиком); `API_LOG_ENABLED=0` — выключить. Первое, куда
смотреть, когда «перестало работать» что-то, завязанное на внешний сервис.
Рядом — `app-ГГГГ-ММ-ДД.log`: предупреждения и ошибки самого приложения
с трассировкой (в т.ч. то, что пользователь видит как «Проверьте правильность
заполнения формы»). Этот журнал и логи cron-скриптов можно смотреть прямо на сайте: меню
«Администрирование → Логи сервера» (только председатель) — хвост файла,
поиск, фильтр «только ошибки», скачивание.
В журнале есть персональные данные из ответов (ФИО и ИНН плательщиков в
выписке) — не выкладывать его целиком в открытый доступ.

## Автоматизация (cron)

Все обёртки `scripts/*.sh` ниже подхватывают `.env` из корня проекта сами
(`.env` НЕ читается через python-dotenv — приложение берёт настройки из
`os.environ` напрямую, см. `.env.example`). Веб-процесс обычно получает
`SECRET_KEY`/`BANK_API_ENCRYPTION_KEY`/`DATABASE_URL` и т.п. через окружение
сервиса (systemd `EnvironmentFile=` и т.п.), а у cron своего окружения нет
— без этого блока в обёртке скрипт из-под cron тихо взял бы дефолты из
`config.py` вместо настоящих продовых значений (например, расшифровка
сохранённых секретов — пароля DVR-регистратора, токенов eWeLink,
`client_secret` банка — попросту не сошлась бы с ключом, которым их
зашифровал веб-процесс). Другой файл окружения можно указать через
`ENV_FILE=/путь/к/файлу` перед командой — так настраивается второй
кооператив с того же кода (общая часть обёрток — `scripts/_common.sh`).

Ключевая ставка ЦБ РФ (нужна для расчёта пени) обновляется ежедневным
cron-скриптом — чтобы к моменту месячного начисления пени (см. ниже) она
уже точно была свежей:

```bash
# crontab -e
0 6 * * * /путь/к/проекту/scripts/update_key_rate.sh
```

Скрипт сам подхватывает venv проекта (если есть `.venv/` или `venv/`),
пишет лог в `instance/logs/update_key_rate.log` и не даёт двум запускам
пересечься (`flock`). Запустить вручную для проверки:
`python3 scripts/update_key_rate.py`.

Само начисление пени по просроченным взносам/налогу — раз в месяц, тоже по
cron, не при заходе на сайт (раньше accrue_penalties() вызывалась тихо на
каждом открытии дашборда/страницы «Пеня» — от этого отказались: начисление
происходило неочевидно для правления и раздувало историю начислений
построчно почти на каждый день при частых заходах):

```bash
# crontab -e
10 6 1 * * /путь/к/проекту/scripts/accrue_penalty.sh
```

Тот же принцип (venv, `flock`, лог `instance/logs/accrue_penalty.log`), время
запуска — чуть позже `update_key_rate.sh`, чтобы ставка на начало месяца уже
была подтянута. Запустить вручную для проверки: `python3 scripts/accrue_penalty.py`.

Стоимость SMS с кодом восстановления пароля (платная услуга, см.
предупреждение на странице восстановления пароля) SMS Aero отдаёт не сразу
при отправке, а некоторое время спустя — отдельный скрипт раз в сутки
досчитывает её и начисляет на личный счёт получателя (вид взноса
«Телекоммуникационные услуги и споры», туда же вручную начисляется
госпошлина по искам, см. [«Делопроизводство»](features/legal-docs.md)):

```bash
# crontab -e
30 3 * * * /путь/к/проекту/scripts/reconcile_sms_charges.sh
```

Тот же принцип (venv, `flock`, лог `instance/logs/reconcile_sms_charges.log`,
`.env`). Записи, для которых провайдер ещё не посчитал стоимость, просто
остаются в очереди до следующего запуска. Запустить вручную для проверки:
`python3 scripts/reconcile_sms_charges.py`.

Расчётные счета кооператива с настроенной интеграцией с API банка (баланс
и выписка за последние 7 дней — та же логика, что у кнопок «Обновить
баланс»/«Загрузить из банка» на странице счетов) обновляются по будням
рано утром, до начала рабочего дня:

```bash
# crontab -e
0 7 * * 1-5 /путь/к/проекту/scripts/sync_bank_accounts.sh
```

Тот же принцип (venv, `flock`, лог `instance/logs/sync_bank_accounts.log`,
`.env`). Счета без настроенной интеграции просто пропускаются, это не
ошибка. Запустить вручную для проверки: `python3 scripts/sync_bank_accounts.py`.

Баланс личного кабинета контрагентов с настроенным API (см.
[«Контрагенты»](features/finance.md): SMS Aero, Beget.com, ТНС-Энерго
Бизнес) — отдельным скриптом, со своим логом:

```bash
# crontab -e
10 7 * * * /путь/к/проекту/scripts/sync_counterparty_balances.sh
```

Тот же принцип (venv, `flock`, лог `instance/logs/sync_counterparty_balances.log`,
`.env`). Контрагенты без настроенной интеграции просто пропускаются.
Скрипт запускается каждый день, но баланс контрагента обновляется не при
каждом запуске, а с интервалом, выбранным в его карточке («раз в сутки» …
«раз в месяц») — у контрагентов, чей баланс меняется каждый день (SMS Aero),
ежедневное обновление давало запись в журнале аудита на каждый день.
Запустить вручную для проверки: `python3 scripts/sync_counterparty_balances.py`.

Мониторинг электроэнергии по фазам (см. раздел [«Мониторинг электропитания»](features/garages.md))
опрашивает облако eWeLink раз в минуту тем же способом — отдельный
cron-скрипт, а не фоновый поток внутри веб-процесса:

```bash
# crontab -e
* * * * * /путь/к/проекту/scripts/poll_ewelink.sh
```

Тот же принцип (venv, `flock`, лог `instance/logs/poll_ewelink.log`). Логи
всех cron-скриптов ротируются сами (`rotate_log` в `scripts/_common.sh`):
больше 5 МБ — лог сдвигается в `*.log.1`, `*.log.2.gz`, `*.log.3.gz` (архивы
со второго сжимаются gzip), самый старый удаляется;
настраивается переменными `LOG_MAX_BYTES`/`LOG_KEEP` в `.env`. Отдельный
logrotate не нужен.

Запустить вручную для проверки: `python3 scripts/poll_ewelink.py`.

Превью-кадры с камер видеонаблюдения (см. раздел [«Видеонаблюдение»](features/surveillance.md))
снимаются тем же способом, тоже раз в минуту:

```bash
# crontab -e
* * * * * /путь/к/проекту/scripts/dvr_snapshot.sh
```

Тот же принцип (venv, `flock`, лог `instance/logs/dvr_snapshot.log`, ротируется сам — см. выше). Требует
системный бинарник `ffmpeg` (не Python-пакет, не в `requirements.txt`,
устанавливается отдельно — например `apt install ffmpeg`); без него скрипт
сразу завершается с понятной ошибкой в лог, ничего не пытаясь. Запустить
вручную для проверки: `python3 scripts/dvr_snapshot.py`.

Резервное копирование БД — тем же способом, ежедневно ночью:

```bash
# crontab -e
0 3 * * * /путь/к/проекту/scripts/backup_db.sh
```

Копирует `instance/coop.db` через `sqlite3`-backup API (безопасно даже
во время активной записи — SQLite гарантирует консистентный снимок, в
отличие от голого `cp`) и сжимает gzip (`coop_ГГГГММДД_ЧЧММСС.db.gz`, ~в 5 раз
меньше; распаковать вручную — `gunzip -k`) в `instance/backups/`, хранит
последние 30 копий (настраивается через `KEEP_BACKUPS`). **Бэкап лежит на том же диске, что и
сама БД** — это защита от повреждения файла/случайной команды `rm`, а не
от отказа сервера целиком: от него — [внешний бэкап](#внешний-бэкап)
ниже. Запустить вручную: `python3 scripts/backup_db.py`.

### Внешний бэкап

Хостер может потерять VPS вместе со всеми своими бэкапами (с Beget так и
случилось): копии на том же сервере и у того же провайдера не спасают. Поэтому копий три, у
трёх независимых сторон:

| Копия | Чем | Где |
|---|---|---|
| снимки БД | `backup_db` (выше) | сам сервер, `instance/backups/` |
| внешняя | `backup_offsite` → restic | Яндекс.Диск (через rclone) |
| локальная | агент [`agents/backup/`](../agents/backup/README.md) | компьютер председателя |

Во внешнюю и локальную копии попадают снимок БД, файл окружения (`.env`:
без `SECRET_KEY`/`BANK_API_ENCRYPTION_KEY` сохранённые в БД пароли и токены
не расшифровать), `uploads/`, `bank_certs/`, `bundles/` и архив почты
`mail_backup/`. Каталог `dvr/` не входит.

Фото (jpg/png/webp) при загрузке на сайт уменьшаются до 2000 px по
длинной стороне и пережимаются, EXIF убирается
([`app/images.py`](../app/images.py)). Снимок с телефона занимает около
0,8 МБ вместо 5–8 МБ. Фото, загруженные до этого, ужимаются один раз
вручную, имена файлов и БД при этом не меняются:

```bash
sudo -u coop /home/coop/garage_coop/scripts/shrink_uploads.sh --dry-run   # сколько освободится
sudo -u coop /home/coop/garage_coop/scripts/shrink_uploads.sh
```

```bash
# crontab -e (ansible ставит эти строки сам, см. cron_jobs в defaults.yml)
50 2 * * * /путь/к/проекту/scripts/backup_mailbox.sh
20 3 * * * /путь/к/проекту/scripts/backup_offsite.sh
```

**`backup_mailbox`** копирует письма почты правления с почтового сервера
(настройки — из «Почты правления», отдельный конфиг не нужен) в
`instance/mail_backup/` файлами `.eml`. IMAP: все папки, только чтение (флаг
«прочитано» не меняется). POP3: по UIDL. Работает только на добавление:
удалённое на сервере письмо в архиве остаётся. Почта не настроена — скрипт
просто выходит.

**`backup_offsite`** каждый раз обновляет `instance/backup_staging/`
(консистентный снимок БД, копия `.env`, `MANIFEST.json`), который забирает
агент председателя. Если в `.env` задан `RESTIC_REPOSITORY`, он же
отправляет всё это в restic-репозиторий: шифрование на сервере, история
версий, передаются только изменения. Политика хранения:
`OFFSITE_KEEP_DAILY`/`WEEKLY`/`MONTHLY` (14/8/12), по воскресеньям
`restic check`. Итог запуска — `instance/logs/backup_offsite_status.json`.

Настройка Яндекс.Диска (restic ходит туда через rclone):

1. На компьютере с браузером (rclone там тоже нужен) войти в Яндекс
   аккаунтом кооператива, а не личным:
   ```bash
   rclone authorize "yandex"
   ```
   Браузер откроет страницу входа. После входа в терминале будет JSON
   между `--->` и `<---`: это токен.
2. Через ansible: в `vars.yml` вписать `rclone_yandex_token: '<JSON>'`.
   Плейбук создаст `~/.config/rclone/rclone.conf` пользователя сайта с
   remote `yadisk`. Дальше rclone сам продлевает токен и пишет новый в
   этот же файл, поэтому плейбук его не перезаписывает. Чтобы заменить
   токен, удалите файл на сервере и прогоните плейбук.
   Без ansible: `sudo -u coop rclone config create yadisk yandex token '<JSON>'`.
3. В `.env` на сервере (через ansible — `app_env_extra` в `vars.yml`, см.
   `vars.example.yml`):
   ```
   RESTIC_REPOSITORY=rclone:yadisk:coop-backup
   RESTIC_PASSWORD=<openssl rand -hex 32>
   ```
   **`RESTIC_PASSWORD` сохраните вне сервера** (менеджер паролей правления):
   копия `.env` лежит внутри того же зашифрованного репозитория, и без
   пароля её не достать.
4. Проверка под пользователем сайта: `sudo -u coop rclone lsd yadisk:`,
   затем `sudo -u coop scripts/backup_offsite.sh` (первый запуск сам
   выполнит `restic init`, лог — `instance/logs/backup_offsite.log`) и
   `sudo -u coop sh -c 'set -a; . ./.env; set +a; restic snapshots'`.

На Диске появится папка `coop-backup` с файлами restic. Они зашифрованы:
открывать и переносить их руками бессмысленно, а удалять нельзя.
Бесплатных 5–10 ГБ при нынешнем объёме (около 0,7 ГБ, дальше в основном
прирост) хватит надолго.

Вместо Диска можно взять Yandex Object Storage (S3, платно, копейки):
`RESTIC_REPOSITORY=s3:https://storage.yandexcloud.net/<бакет>/coop` и
статический ключ сервисного аккаунта с ролью `storage.editor` на бакет в
`AWS_ACCESS_KEY_ID`/`AWS_SECRET_ACCESS_KEY`, `AWS_DEFAULT_REGION=ru-central1`.

Восстановление на новом сервере (rclone с тем же токеном или новым из
`rclone authorize "yandex"`):

```bash
rclone config create yadisk yandex token '<JSON>'
export RESTIC_REPOSITORY=rclone:yadisk:coop-backup RESTIC_PASSWORD=…
restic snapshots
restic restore latest --target /tmp/coop-restore
```

Дальше так же, как из локальной копии: раскладка каталогов и подъём
сервера ansible-плейбуком описаны в [agents/backup/README.md](../agents/backup/README.md#восстановление).

Свежесть копий видна председателю на панели: красное предупреждение,
если внешний бэкап упал, не запускался больше 36 часов или не настроен,
или если агент председателя не забирал данные больше трёх дней
(`app/backup_status.py`).

Агент председателя заходит на сервер ssh-ключом, ограниченным
`scripts/backup_pull_gate.sh` (rrsync на чтение внутри `INSTANCE_DIR`).
Каждый его заход пишется в `instance/logs/backup_pull.log`. Если записи
давно не появлялись, локальная копия перестала обновляться.

**Восстановление** — из `scripts/restore_db.py` (обёртка `restore_db.sh`
подхватывает venv так же, как у бэкапа; в cron её ставить не нужно, это
ручная операция):

```bash
# список доступных бэкапов
python3 scripts/restore_db.py --list

# восстановить конкретный (номер из списка, имя файла или latest)
python3 scripts/restore_db.py --restore latest
python3 scripts/restore_db.py --restore 3
python3 scripts/restore_db.py --restore coop_20260829_030000.db.gz
```

Сжатый бэкап распаковывает сам (старые несжатые `.db` тоже понимает). Проверяет `PRAGMA integrity_check` у бэкапа и у результата, восстанавливает
через тот же `sqlite3` backup API и атомарный `os.replace()` (чтобы сбой
посреди записи не испортил рабочую БД), а перед перезаписью сам сохраняет
текущую БД в `instance/backups/` с префиксом `pre_restore_` — так что
неудачное восстановление тоже можно откатить этим же скриптом. Требует
интерактивного подтверждения, если не передан `--yes`.

**Самолечение БД при старте веб-процесса** — `scripts/repair_db.py`
(обёртка `repair_db.sh`, лог `instance/logs/repair_db.log`). SQLite в
режиме WAL переживает падение процесса без повреждения данных, но если
процесс убит жёстко посреди записи (например, OOM killer — а раз это
демон, systemd его тут же перезапускает, но саму БД никто не проверяет)
изредка ломаются B-tree ИНДЕКСОВ, не сами данные. Добавьте вызов перед
стартом сервиса — ExecStartPre в systemd-юните веб-процесса (полный пример
юнита — в [INSTALL.md](../INSTALL.md)):

```ini
[Service]
ExecStartPre=/путь/к/проекту/scripts/repair_db.sh
ExecStart=... (gunicorn/uwsgi и т.п.)
```

Скрипт: `PRAGMA integrity_check` → если "ok", ничего не делает; иначе
`REINDEX` (читает только уже подтверждённо целые табличные данные,
перестраивает по ним индексы — ни одна строка не теряется) и проверяет
ещё раз. Если после `REINDEX` всё ещё не "ok" — значит, повреждены сами
страницы с данными, не только индексы: это НЕ пытается чинить
самостоятельно (тихий авто-восстановление из бэкапа могло бы откатить
свежие данные без ведома человека) — выходит с кодом 1, из-за чего
systemd не запустит сам сервис (лучше явный отказ старта с понятным
сообщением в логе, чем 500-е на битой БД) и явно подсказывает команду:
`python3 scripts/restore_db.py --restore latest`. Запустить вручную для
проверки: `python3 scripts/repair_db.py`.

Очистка «осиротевших» inline-картинок (вставлены через кнопку «Вставить
картинку» в новости/вики/объявление доски/сообщение форума, но сама
статья/страница/объявление/сообщение так и не сохранены — см. разделы
[«Вики», «Доска объявлений», «Форум»](features/communication.md)) — раз в сутки достаточно:

```bash
# crontab -e
30 3 * * * /путь/к/проекту/scripts/cleanup_orphan_attachments.sh
```

Удаляет вложения (`NewsAttachment`, `WikiAttachment`, `BulletinAttachment`,
`ForumAttachment`) без привязки к статье/странице/объявлению/сообщению
старше 24 часов — вместе с самим файлом на диске. Запустить вручную:
`python3 scripts/cleanup_orphan_attachments.py`.

Уведомление правлению о непрочитанных сообщениях в чате правления (см.
раздел [«Уведомления о событиях сайта»](features/people.md)) — порог «не прочитано 10
минут» требует более частой проверки, чем остальные cron-скрипты:

```bash
# crontab -e
*/5 * * * * /путь/к/проекту/scripts/board_chat_digest.sh
```

Тот же принцип (venv, `flock`, лог `instance/logs/board_chat_digest.log`,
`.env`). Уведомляет только тех, кто подписался (`notify_board_chat`) и
ещё не прочитал последнее сообщение чата; повторно — только когда
появляется новое непрочитанное сообщение (`User.board_chat_notified_message_id`
не даёт слать письмо заново на каждый прогон). Запустить вручную для
проверки: `python3 scripts/board_chat_digest.py`.

Бейдж «непрочитано» у почты правления в шапке сайта (см. раздел «Почта
правления» ниже) — число непрочитанных считается не на каждый заход на
сайт (открытие IMAP-соединения может занять до 15 секунд или зависнуть при
недоступном сервере), а этим cron-скриптом:

```bash
# crontab -e
*/5 * * * * /путь/к/проекту/scripts/poll_mailbox.sh
```

Тот же принцип (venv, `flock`, лог `instance/logs/poll_mailbox.log`,
`.env`). IMAP — общий счётчик (настоящие серверные флаги, один на всех);
POP3 сам флагов не хранит, поэтому «прочитано»/«важное» эмулируется
персонально для каждого члена правления в своей таблице (по UIDL, RFC
1939 — см. `app/models.py: MailboxPop3MessageState`), и счётчик тоже
персональный (`User.pop3_mailbox_unread_count`). При первом прогоне для
каждого пользователя вся история на тот момент считается прочитанной
задним числом (бутстрап) — иначе при подключении POP3-почты со старой
историей все увидели бы шквал «непрочитанных» за годы. Если сервер не
поддерживает необязательное расширение UIDL — эмуляция недоступна, бейдж
для POP3 остаётся пустым. Веб-интерфейс (открытие «Входящих»/письма,
клик по точке-индикатору) дополнительно освежает тот же кэш сам в реальном
времени, без похода на сервер отдельно от этого скрипта — см.
`app/mailbox.py: inbox()/view_message()/set_message_state()`. Без
настроенной почты (`MailboxSettings`)
скрипт просто ничего не делает — не ошибка. Запустить вручную для
проверки: `python3 scripts/poll_mailbox.py`.

Привязка Telegram-аккаунтов к уведомлениям (см. раздел «Уведомления о
событиях сайта» ниже) — бот не может написать первым, только ответить
тому, кто сам прислал `/start`, поэтому отдельный скрипт раз в минуту
вычитывает такие сообщения через `getUpdates` (long polling):

```bash
# crontab -e
* * * * * /путь/к/проекту/scripts/poll_telegram.sh
```

Тот же принцип (venv, `flock`, лог `instance/logs/poll_telegram.log`, ротируется сам —
см. выше про `poll_ewelink.log`). Без бота, настроенного на `/telegram/` (только
председатель), скрипт просто ничего не делает — не ошибка. Запустить
вручную для проверки: `python3 scripts/poll_telegram.py`.

Тот же скрипт отвечает на команду `/chatid` (в группе — и `/chatid@имя_бота`)
ID чата, где её отправили. Это нужно для дублирования новостей в группу
Telegram: добавьте бота в группу (для канала — администратором с правом
публикации), отправьте там `/chatid` и впишите полученный ID (`-100…`) в
поле «Группа для новостей» на `/telegram/`. Для публичного канала или группы
можно вписать `@имя`. Новость отправляется в группу сразу при публикации на
сайте (галочка «Опубликовать и в группе Telegram» в форме, по умолчанию
включена). Картинки новости (вставленные в текст и из галереи) уходят
альбомом: если текст влезает в подпись (1024 символа) — одним постом, иначе
двумя сообщениями, порядок выбирается в форме («Сначала картинки, потом
текст»). Остальные файлы — следом, документами. Ограничения Telegram: фото
больше 10 МБ уходит документом, файлы больше 50 МБ не отправляются (правление
увидит предупреждение). Правки новости повторно не отправляются.

### Telegram из РФ

С VPS в России `api.telegram.org` обычно недоступен (`curl -4 https://api.telegram.org/`
висит до таймаута). Запросы бота — и только они, банк/СМС/eWeLink ходят напрямую —
пускаются через внешнюю точку на зарубежном сервере, настраивается на `/telegram/`,
блок «Доступ к Telegram из РФ». Подойдёт самый дешёвый VPS: трафик бота мизерный.

**Вариант 1 — ретранслятор Bot API (nginx).** На зарубежном VPS с доменом и
сертификатом (certbot):

```nginx
server {
    listen 443 ssl;
    server_name tg-relay.example.org;
    ssl_certificate     /etc/letsencrypt/live/tg-relay.example.org/fullchain.pem;
    ssl_certificate_key /etc/letsencrypt/live/tg-relay.example.org/privkey.pem;

    client_max_body_size 50m;          # фото/файлы новостей
    access_log off;                    # в пути запроса — токен бота

    # Только IP нашего сервера — чтобы ретранслятором не пользовались чужие
    allow 203.0.113.10;
    deny all;

    location /bot {
        proxy_pass https://api.telegram.org;
        proxy_ssl_server_name on;
        proxy_set_header Host api.telegram.org;
        proxy_read_timeout 90s;
    }
}
```

На `/telegram/` в поле «Адрес Bot API» — `https://tg-relay.example.org`.

**Вариант 2 — SOCKS-прокси через SSH, без настройки зарубежного сервера**
(нужен только SSH-доступ к нему). На нашем сервере — systemd-юнит:

```ini
# /etc/systemd/system/tg-socks.service
[Unit]
Description=SOCKS-туннель для Telegram
After=network-online.target

[Service]
ExecStart=/usr/bin/ssh -N -D 127.0.0.1:1080 -o ServerAliveInterval=30 -o ExitOnForwardFailure=yes -i /root/.ssh/tg_tunnel tunnel@foreign.example.org
Restart=always
RestartSec=10

[Install]
WantedBy=multi-user.target
```

`systemctl enable --now tg-socks`, затем на `/telegram/` в поле «Прокси» —
`socks5h://127.0.0.1:1080` (`socks5h` — имя api.telegram.org резолвит удалённая
сторона). Нужен пакет PySocks (есть в requirements.txt).

В обоих вариантах TLS до Telegram сквозной (сертификат проверяется), промежуточный
сервер содержимого не видит — кроме ретранслятора из варианта 1, который сам
завершает TLS и видит токен в пути: это должен быть свой сервер. Проверка — кнопка
«Проверить подключение» на `/telegram/`.

## Агент ЭЗП (Почта России)

Заказные письма уходят в Почту через API ИС ЭПС («Система-Система»).
Для этого нужен КЭП кооператива: им подписывается PDF и он же служит
клиентским сертификатом двустороннего ГОСТ-TLS. Ключ КЭП от ФНС
неэкспортируемый, он на Рутокене у председателя, поэтому на сервере сайта
ничего не ставится и в `.env` ничего не добавляется. Работу делает **агент
ЭЗП** — отдельная программа из каталога [`agents/ezp/`](../agents/ezp/README.md)
на компьютере с токеном. На этом компьютере нужны:
- КриптоПро CSP и пакет `cprocsp-stunnel`;
- две systemd-службы: `ezp-stunnel` (туннель до Почты) и `ezp-agent`
  (опрос сайта раз в 5 минут, подпись, отправка, статусы);
- конфиг `/etc/ezp-agent/ezp_agent.ini`, где лежат ID/token отправителя от
  Почты и ПИН токена.

Агент сам ходит на сайт по HTTPS (`/postal-letters/agent/…`, свой
Bearer-токен), так что компьютер может быть за NAT. Сайт хранит только
несекретный ID отправителя и хэш токена агента: «Заказные письма» →
«Настройки API Почты».

Порядок подключения:
1. Отправить сертификаты (клиентский `gm-voshod.cer`, промежуточный ФНС
   `CA_FNS_Russia_2025_01.crt`, корневой ГОСТ Минцифры
   `Mincifry_Rossii_root_guc2022.cer` — см. [`agents/ezp/certs/`](../agents/ezp/certs/README.md)) на ezp.support-r00@russianpost.ru
   и получить тестовые ID/token.
2. Установить агента по [README](../agents/ezp/README.md).
3. Выполнить `ezp_agent.py check`.
4. Отправить три тестовых письма из тестового комплекта.
5. Перейти на продуктив: сменить адрес в `stunnel.conf` и пару ID/token.

## Несколько кооперативов на одном сервере

Ansible-плейбук делает всё ниже сам по списку `coop_extra_instances`
(`deployment/ansible/README.md`, «Несколько кооперативов на одном
сервере»). Ниже описана та же схема для ручной установки.

Каждый кооператив — отдельный экземпляр сайта: своя БД, свои файлы, свой
`.env` (свои `SECRET_KEY`/`BANK_API_ENCRYPTION_KEY`), свой процесс gunicorn
и свой crontab. Код — один checkout на всех (обновляется один раз,
миграции каждый экземпляр накатывает сам при старте). Данные разных
кооперативов физически не пересекаются — общей БД с разделением по
домену в проекте нет намеренно: одна забытая фильтрация в любом из сотен
запросов показала бы персональные данные чужого кооператива.

1. Отдельный пользователь ОС и каталог данных, например `coop2` и
   `/home/coop2/instance`. Доступ к коду на чтение (и к `venv`).
2. Файл окружения `/home/coop2/coop.env` (права `600`, владелец `coop2`):

   ```bash
   INSTANCE_DIR=/home/coop2/instance
   SECRET_KEY=...                # свой, не как у первого кооператива
   BANK_API_ENCRYPTION_KEY=...   # свой
   FORCE_HTTPS=1
   # RECAPTCHA_* — ключи выпускаются на домен, у второго сайта свои
   ```

   `DATABASE_URL` можно не задавать — БД ляжет в `$INSTANCE_DIR/coop.db`.
3. systemd-юнит (копия юнита первого, со своими пользователем, файлом
   окружения и портом):

   ```ini
   [Service]
   User=coop2
   EnvironmentFile=/home/coop2/coop.env
   WorkingDirectory=/путь/к/проекту
   ExecStartPre=/usr/bin/env ENV_FILE=/home/coop2/coop.env /путь/к/проекту/scripts/repair_db.sh
   ExecStart=/путь/к/проекту/venv/bin/gunicorn -w 1 --threads 4 -k gthread -b 127.0.0.1:8001 run:app
   ```

4. vhost nginx на домен второго кооператива → `127.0.0.1:8001`, свой
   сертификат certbot.
5. crontab пользователя `coop2` — те же строки, что и у первого, с
   `ENV_FILE` и сдвигом по минутам, чтобы скрипты двух кооперативов не
   стартовали одновременно:

   ```bash
   # crontab -e (пользователь coop2)
   ENV_FILE=/home/coop2/coop.env
   COOP_CRON_LOCK=/var/lib/coop-cron/cron.lock
   35 3 * * * /путь/к/проекту/scripts/backup_db.sh
   ...
   ```

   Переменные в начале crontab (синтаксис cron, не shell) действуют на все
   строки ниже. Явно указанный, но отсутствующий `ENV_FILE` — ошибка
   запуска, а не тихий откат на `.env` первого кооператива.

Главная ловушка — **забытый `ENV_FILE`**: обёртка тогда возьмёт `.env`
из корня проекта и дефолтный `instance/`, то есть данные первого
кооператива. Защита от этого — права, а не внимательность: когда
кооперативов больше одного, у каждого (включая первый) свой пользователь,
свой файл окружения вне каталога проекта и свой `INSTANCE_DIR` с правами
`700`, а `.env` в корне проекта не лежит вовсе. Тогда ошибка в настройке —
отказ «нет доступа» в логе, а не запись в чужую БД.

### Память (сервер на 1 ГБ)

Каждый процесс приложения — ~120 МБ, и столько же каждый запущенный
cron-скрипт (он поднимает приложение целиком). Ориентир для двух
кооперативов: ~200 МБ система и nginx + 2 × ~130 МБ сайты
(`-w 1 --threads 4`, см. [Деплой в проде](#деплой-в-проде)) + до ~120 МБ
на время cron-скрипта.

- **Общая блокировка cron** — `COOP_CRON_LOCK` (в crontab ВСЕХ
  кооперативов один и тот же путь): одновременно выполняется не больше
  одного скрипта, остальные ждут до `COOP_CRON_LOCK_TIMEOUT` секунд (по
  умолчанию 600) и затем пропускают запуск. Файл должен открываться всеми
  пользователями кооперативов — создайте его заранее вне `/tmp` (в
  `/tmp` с `fs.protected_regular` чужой файл не открыть):

  ```bash
  sudo install -d -m 0755 /var/lib/coop-cron
  sudo install -m 0666 /dev/null /var/lib/coop-cron/cron.lock
  ```

- Частые скрипты (`poll_telegram`/`poll_ewelink` раз в минуту,
  `board_chat_digest`/`poll_mailbox` раз в 5 минут) включайте только там,
  где соответствующая интеграция реально настроена.
- Запас на пики (генерация PDF, наложение cron-скрипта на запрос) —
  zram или swap на 0,5–1 ГБ.

# Документы, собрания, реквизиты, правление

[← К оглавлению](../../README.md)

## Документы, собрания, реквизиты
- **Документы** — устав/приказы/акты/письма/протоколы, с загрузкой файла;
  фильтр по типу — выпадающий список, переходит по выбору (без отдельной
  кнопки «Применить»). Необязательная привязка к контрагенту
  (`Document.counterparty_id`) — задаётся вручную в форме документа (только
  правление) либо проставляется сама при прикреплении файла к расходу/
  платежу/акту сверки контрагента; в списке документов появляется
  отдельный фильтр «Контрагент» (виден только правлению, вместе с колонкой
  «Контрагент», ссылкой на его карточку)
- **Общие собрания** — дата, повестка, секретарь, председательствующий,
  протокол (загрузка файла прямо из модалки создания); служат основанием
  для созывов правления и составов ревизионной комиссии (см. выше)
- **Годовой отчёт председателя** (`/annual-reports/`, составляется на
  собрании, отмеченном как годовое отчётное) — отчёт о расходах и
  финансовая отчётность (два файла), смета на следующий год (сумма и
  отметка об утверждении собранием), ставки взносов на следующий год по
  каждому виду взноса (`AnnualReport`/`FeeRate`); составить/изменить может
  только председатель, сам отчёт виден любому вошедшему; ссылка на
  составление/просмотр — прямо в списке собраний и на дашборде
- **Реквизиты кооператива** — ИНН/КПП/ОГРН, площади (кооператива, под
  гаражами, общего пользования); краткое название используется в шапке
  вместо статичного «ГСК»
- **Расчётные счета** (`/finance/bank-accounts`, ссылка в меню «Кооператив»
  → «Финансы», раньше жили прямо на странице «О кооперативе») — несколько
  счетов (в одном или разных банках), с пометкой основного — именно он
  берётся для ПД-4; у каждого расчётного счёта отдельно — фактический
  баланс, с датой сверки: вручную (по умолчанию) или автоматически, если
  для счёта подключён API банка (см. ниже). Поле «Баланс» самого кооператива
  (в отличие от баланса каждого расчётного счёта) — не хранится в БД,
  считается на лету как `accounting.cooperative_balance()` — сумма по всем
  расчётным счетам (сколько реально денег у кооператива), не путать с
  `receivables_balance()` (сколько члены должны/переплатили — отдельная
  метрика, нигде в UI сейчас не выведена). Расчётные
  счета целиком, а также поля «Баланс» и «Комментарий» в реквизитах —
  видны только правлению (`is_board()`), остальные реквизиты — всем
- **API банка на расчётном счёте** (`app/bank_api/`, доступно
  председателю) — у Сбербанка, ВТБ и Т-Банка есть API для организаций, но
  реализована пока только сторона Сбербанка (СберБизнес); ВТБ и Т-Банк уже
  можно выбрать в списке — интерфейс честно помечает их как «интеграция
  ещё не реализована», а не притворяется, что что-то работает. Для счёта
  со включённым API (кнопка «Настроить API»: client_id/client_secret,
  тестовый/промышленный контур — секрет хранится зашифрованным, не в
  открытом виде; плюс клиентский mTLS-сертификат — банк требует его для
  самого соединения, см. ниже):
  - **Баланс** — обновляется одной кнопкой вместо ручного ввода
  - **Выписка** (`/bank-accounts/<id>/statement`) — зачисления и списания
    за период, с дедупликацией повторных загрузок по номеру операции в
    банке. Если банк указал в назначении платежа номер лицевого счёта
    (например, «ЛС 10640; ЧЛЕНСКИЕ ВЗНОСЫ (ФАМИЛИЯ И.О.)», а также
    варианты «Л/С» и «ЛСИ», которые тот же банк может использовать
    вперемешку) и такой счёт есть в системе — зачисление автоматически
    гасит задолженность полной поступившей суммой (комиссию банка, если
    она удержана, кооператив берёт на себя, не вычитает из погашения) без
    подтверждения. Если номера нет — тот же поиск по ФИО плательщика или
    того, за кого платят (форма «Фамилия И.О.» в самом назначении
    платежа), включая лиц для связи по гаражу — они поднимают счета
    владельцев гаража, не свой собственный. Автоматически — только когда
    результат однозначен (при нескольких видах взноса на гараж помогает
    сужение по слову в назначении платежа, например «ЗЕМЕЛЬНЫЙ НАЛОГ»); в
    остальных случаях — ручная кнопка «Разнести» прямо на странице
    выписки, с возможностью явно указать номер счёта, либо кнопка
    «Разнести всё возможное» — пересчитывает разом все ещё неразнесённые
    зачисления счёта (полезно после добавления нового лицевого счёта).
    Агрегированные проводки по реестру платежей (одна сумма сразу за
    нескольких плательщиков, узнаваемая по фразе «ПО ПРИНЯТЫМ ПЛАТЕЖАМ...»
    в назначении) помечаются отдельно и не предлагаются к разнесению —
    их разносят через реестр платежей, а не выписку
  - **Реестр начислений** (`/bank-accounts/<id>/registry/charges`) — вся
    текущая непогашенная задолженность по лицевым счетам (взносы, налог,
    электричество — те же `accounting.balance() < 0`, что видны на
    карточках лицевых счетов) отправляется в банк единым пакетом:
    плательщики видят её и могут оплатить прямо в приложении банка по
    своему лицевому счёту, без реквизитов кооператива под рукой. Есть и
    кнопка «Скачать файл реестра» — тот же CP1251-файл, что и в
    автоматическую отправку, для ручной загрузки на случай, если
    автоматическая отправка через API недоступна для конкретного
    подключения
  - **Реестр платежей** (`/bank-accounts/<id>/registry/payments`) —
    платежи, поступившие в банк по реестру начислений; кнопка «Разнести»
    у записи находит лицевой счёт по номеру (а если его в записи нет — по
    тому же поиску по ФИО/лицам для связи, что и в выписке) и заводит
    обычный `Payment` на сумму НАЧИСЛЕНИЯ (не за вычетом банковской
    комиссии — комиссия показывается отдельно, для сверки, и не должна
    восприниматься как недоплата члена) с разнесением по `FIFO` — тем же
    путём, что и платёж, введённый вручную. Тоже с ручным запасным путём —
    загрузить CP1251-файл, скачанный из СберБизнес Онлайн, вместо запроса
    через API
  - **Формат обоих файлов — настраиваемый**
    (`/bank-accounts/<id>/registry/format`, кнопка «Настроить формат
    файла» на страницах реестров) — состав и порядок полей, разделитель
    дробной части суммы (у реестра начислений и у реестра платежей он, как
    правило, разный — точка/запятая), разделитель полей, кодировка, код
    услуги/периода, префикс строки-сводки в конце файла реестра платежей.
    Тот же принцип UI, что у настройки формата CSV-импорта в мастере
    первого запуска: каталог полей + чекбокс/позиция, без
    drag-and-drop. **Формат по умолчанию — не выдуманный, а реальный**,
    полученный по образцам файлов от кооператива: реестр начислений —
    `лицевой_счёт;ФИО;назначение;код_услуги;сумма` (5 полей, точка); реестр
    платежей — 13 полей (дата/время/код отделения/ID терминала/номер
    операции/лицевой счёт/ФИО/назначение/код услуги/сумма начисления/сумма
    зачисления/комиссия/код статуса), запятая, плюс завершающая
    строка-сводка с распознаваемым префиксом (`=...`), которая пропускается
    при разборе
  **Перед включением обязательны три вещи, без которых API Сбербанка не
  заработает вообще** (подтверждено официальной документацией и живым
  подключением тестового контура, не только предположениями):
  1. **access_token/refresh_token, а не только client_id/secret** —
     Sber API работает от имени конкретного пользователя СберБизнес, а не
     по client_credentials. Получите пару access_token/refresh_token в
     личном кабинете Sber API («Ключи доступа» → сгенерировать) и введите
     refresh_token в модалке «Настроить API» (access_token вводить не
     нужно — обновляется автоматически). Банк может при обновлении
     выдать новый refresh_token взамен старого — приложение отслеживает
     это само, ничего вручную обновлять не нужно;
  2. клиентский mTLS-сертификат счёта (.pfx/.p12 из личного кабинета
     Sber API — загружается в той же модалке «Настроить API», конвертация
     в PEM происходит на сервере, исходный файл и пароль не сохраняются;
     сохраняется вся цепочка сертификатов из контейнера, не только лист);
  3. `SBERBANK_API_CA_BUNDLE` — доверенные сертификаты банка (**УЦ Сбера
     И НУЦ Минцифры России** — обе цепочки, не общемировой центр
     сертификации) на сервере приложения; готовые архивы для скачивания
     — прямо от банка, ссылки в `.env.example`.
  Тестовый контур (`https://fintech-test.sberbank.ru:9443`) подтверждён
  напрямую личным кабинетом кооператива. Адреса остальных ресурсов API
  (баланс, выписка, реестры) и промышленный контур — по-прежнему по
  открытой документации, не проверены живым запросом; формат самих
  файлов реестров, в отличие от адресов ресурсов, — подтверждён реальными
  образцами, не догадка. Официальный перечень операций (scope) не
  содержит явной операции для реестра начислений — возможно, это
  отдельный от Sber API продукт, требующий уточнения у банка; подробности
  и что уточнить перед боевым включением см. в `context.md` и комментариях
  `app/bank_api/sberbank.py` и `app/bank_api/registry_file.py`
- **Электронное голосование** (`/voting`) — очно-заочное или заочное,
  альтернатива очному собранию, когда не удаётся очно собрать всех
  собственников. Председатель создаёт голосование (черновик), формирует
  повестку из одного или нескольких вопросов (у каждого — свой
  настраиваемый порог принятия, напр. 0.5 для простого большинства или
  0.6667 для квалифицированного), затем явно открывает приём бюллетеней
  на заданный период. Голосуют владельцы гаражей — вес голоса человека
  равна сумме его долей владения по всем его гаражам, так что «1 гараж —
  1 голос», а при нескольких собственниках гаража их голос делится ровно
  по долям, без специального кода под этот случай. Переголосование, пока
  приём открыт, разрешено — учитывается последняя подача. Кворум — жёсткое
  правило: голосование правомочно, только если приняло участие строго
  больше 50% от общего числа голосов кооператива; порог принятия по
  каждому вопросу считается от общего числа голосов кооператива (не от
  числа проголосовавших) — вопрос не считается принятым без кворума, даже
  при формально достаточной доле «за». Результаты видны правлению всегда,
  рядовым членам — только после закрытия голосования (чтобы не влиять на
  ещё не проголосовавших). При подаче бюллетеня можно оставить необязательный
  комментарий по каждому вопросу — обоснование своего голоса; в отличие от
  агрегированных итогов, комментарий ПУБЛИЧНЫЙ и виден всем сразу, не
  дожидаясь закрытия голосования. Итоговый подписанный протокол
  прикрепляется вручную (как и у очных собраний) — не генерируется
  автоматически
- **Предложения голосований** (`/proposals`) — любой член кооператива
  (собственник хотя бы доли гаража) может предложить тему для общего
  голосования, не будучи в правлении. Предложение (тема + описание) уходит
  правлению на рассмотрение: каждый член ТЕКУЩЕГО созыва голосует «за»/
  «против»/«воздержался» вынесения на общее голосование — по головам
  (один человек — один голос), а не по долям владения, в отличие от
  самого голосования; «воздержался» не засчитывается ни в чью пользу.
  Пока предложение ожидает решения, председатель может поправить
  формулировку. Решение подводится автоматически — как только
  проголосовали все члены текущего созыва, либо (если кто-то не успел) по
  истечении недели с момента подачи: голосов «за» больше, чем «против» →
  предложение одобрено и тут же заводится черновик обычного голосования
  (`/voting`) с тем же названием/описанием — председателю остаётся
  сформировать повестку и открыть его обычным путём; иначе → отклонено.
  Ничья (в т.ч. если никто из правления не проголосовал за неделю, или все
  воздержались) считается отклонением. При голосовании член правления
  тоже может оставить публичный комментарий — виден всем, включая
  рядовых членов, независимо от статуса предложения
